# V1 — 사장님용 네일샵 운영 관리

## 문서 목적과 상태

대화에서 합의한 출시 범위와 업무 규칙을 보존하고, 이후 작은 스토리를 작성하는 기준으로 사용한다.
기능 범위 합의 단계이며 개별 스토리 승인·구현·검증 완료를 뜻하지 않는다.
활성 구현 스토리 없음. 미정 항목을 해결한 뒤 STORY.md 양식으로 스토리를 작성한다.

## 사용자와 운영

- 첫 도입 대상은 사용자 아내의 네일샵. 현재 사장님 포함 시술자 2명이며 인원 변경을 지원한다.
- 사장님과 직원이 하나의 기기에서 사장님 로그인 세션을 공유한다. 직원별 로그인·권한 시스템은 제외한다.
- 로그인 계정과 예약 담당자는 다른 개념이다. 사장님도 예약 담당자가 될 수 있다.
- 향후 다른 서비스 업종 확장이 목표지만, 초기 다업종 기능이나 범용 엔진은 만들지 않는다.

## 확정 업무 규칙

### 예약과 일정

- 담당자별 독립 일정 화면은 필수가 아니다. 담당자별 예약·가용시간 데이터는 필수다.
- V1은 사장님이 담당자의 반복되는 기본 근무시간과 날짜별 변경(출퇴근 시간·휴무)을 관리한다. 직원 로그인·직원 직접 스케줄 입력은 추가하지 않는다.
- 날짜별 변경이 있으면 해당 날짜에 우선 적용한다. 예약 가능 구간은 해당 날짜의 근무시간에서 예약·차단 구간을 제외해 판단한다.
- 샵 영업시간과 담당자 기본 근무시간의 상속 관계, 기존 예약과 충돌하는 근무시간 변경 처리 규칙은 아직 미정이다.
- 예약 생성·변경 과정에서 대상 담당자의 예약·차단 시간과 가용 여부를 확인할 수 있어야 한다.
- 기존 활성 예약과 겹치는 시간 차단은 불가. 먼저 예약을 명시적으로 이동하거나 취소한 뒤 다시 차단한다.
- 차단을 이유로 기존 예약을 자동 취소하거나 이동하지 않는다.
- 예약 변경은 날짜·시간·담당자 변경을 포함한다. 변경 실패 시 기존 예약을 유지한다.
- 시술 소요시간은 시술별 기본값을 사용하며, 담당자별 값이 있으면 덮어쓴다. 선택한 시술들의 시간을 합산한다.
- 시술 가격도 시술별 기본값을 사용하며, 담당자별 가격이 설정되어 있으면 해당 값을 우선 적용한다. 담당자별 설정이 없으면 기본 가격을 사용한다.
- 가격 설정 변경의 기존 예약 반영 여부 및 담당자 변경 시 가격 재계산 규칙은 아직 확정하지 않았다.
- 담당자 변경 시 새 담당자의 소요시간으로 종료시간을 재계산한다. 전체 구간이 다른 예약·차단과 겹치면 변경 불가다.
- 소요시간 설정 변경만으로 기존 예약 시간을 바꾸지 않는다. 새 예약부터 적용한다.
- 담당자 변경 이외의 기존 예약 편집 시 최신 시간 설정을 재적용할지는 미정이다.
- 사장님 직접 예약은 분 단위 자유 입력을 허용한다. 충돌 여부는 전체 예약 구간으로 검사한다.
- 고객과 예약 이동·취소를 조율하는 일은 전화 등 서비스 밖에서 진행한다.
- 취소된 예약은 삭제하지 않는다. 기본 타임테이블에서 제외하고 해당 예약이 점유한 시간을 해제한다. 다른 예약·차단·근무시간 제약은 유지한다.
- 원래 예약 내용·취소 시각·취소 사유를 보관한다. 완료 처리 시 완료 시각을 남긴다.
- 별도 상태 필드를 강제하지 않는다. 완료·취소 시각으로 예정/완료/취소를 구분하는 최소 구조를 기준으로 삼는다.
- 취소 요청의 진위 확인과 분쟁 대응은 운영으로 처리한다. 고객 취소 의사를 입증하는 별도 기능이나 공유 로그인 내 실제 처리자 식별 기능은 V1에 추가하지 않는다.
- 점심·휴무는 별도 기능이 아니라 일반 시간 차단으로 표현한다. 직원 휴무 신청·승인 기능은 제외한다.

### 회원권과 결제

- 회원권은 금액 충전형으로 고정한다. 횟수형·유형 선택 설정은 제외한다.
- 충전액이 잔액에 더해지며 사용액이 차감된다. 충전·차감·정정 이력을 추적할 수 있어야 한다.
- 잔액 입력 오류는 전체 거래 취소·재등록을 강제하지 않고, 사장님이 차액과 사유를 입력해 잔액을 증감하는 방식으로 정정한다.
- 모든 잔액 변경에 증감액·변경 전후 잔액·처리 시각·사유를 기록한다. 예: 과충전 정정 -1만 원, 사유 '실수로 1만 원 과충전'.
- 잔액 조정은 실제 결제·환불과 별개이며 매출을 변경하지 않는다. 사유 문구를 해석해 매출을 자동 변경하지 않는다.
- V1은 금액 오입력 유형별 전용 정정 기능을 만들지 않는다. 사장님이 대상(회원권 잔액 또는 결제·매출 기록)을 구분해 금액을 증감하고 시각·금액·사유와 변경 이력을 남긴다.
- 회원권 잔액 조정은 잔액만 변경하며, 결제·매출 조정은 해당 매출 집계에 반영한다. 서로 자동 연동하지 않는다.
- 자유로운 증감은 입력 권한을 뜻하며 기존 검증을 제거하지 않는다. 회원권 잔액 정정에도 마이너스 잔액 금지 규칙을 적용한다.
- 실제 결제액과 충전액은 별도 금액으로 기록한다.
- 예: 결제 27만 원 / 충전 30만 원, 또는 결제 30만 원 / 충전 33만 원.
- 할인·보너스 자동 계산이나 프로모션 관리 없이 사장님이 금액을 입력한다.
- 입력 토글·모달 등 상세 UX는 보류한다.
- 실제 결제 처리·PG·온라인 결제 연동은 제공하지 않는다.
- 회원권 잔액이 부족하면 잔액 범위에서 차감하고, 나머지는 서비스 밖에서 받은 별도 결제로 기록한다. 마이너스 잔액·외상은 제외한다.
- 예: 시술비 5만 원 / 잔액 3만 원이면 회원권 3만 원 차감 + 별도 결제 2만 원 기록. 매출에는 실제 받은 2만 원만 반영한다.
- V1 매출은 실제 결제액 기준이다. 회원권 판매 시 실제 받은 금액은 포함하고, 회원권 잔액 사용은 추가 매출로 집계하지 않는다.
- 완료된 시술 금액 기준 실적 및 회원권 별도 대시보드 지표는 필요할 때 추가한다. 결제일·취소·정정·환불의 집계 날짜 규칙은 미정이다.
- V1 회원권 환불은 해지 환불만 지원한다. 일부 환불 후 계속 사용하는 방식은 제외한다.
- 환불액은 가게 정책에 따라 사장님이 직접 산정·입력한다. 시스템에 가게별 환불 계산식을 구현하지 않는다.
- 환불 처리 시 해당 회원권의 남은 잔액 전부를 소멸하고 사용 종료한다. 실제 환불액·소멸 잔액·사유·처리 시각을 기록하며 원래 결제·충전·사용 이력은 삭제하지 않는다.
- 매출 집계에는 소멸 잔액이 아닌 실제 환불액만 자동 차감 반영한다. 돈을 돌려주는 행위는 서비스 밖에서 처리한다.
- V1은 샵 내 고객별 회원권 잔액 하나로 관리한다. 추가 충전은 기존 잔액에 합산하되 충전별 실제 결제액·충전액·이력을 보관한다.
- 해지 환불 시 고객의 합산 회원권 잔액 전체를 소멸한다. 여러 회원권을 따로 보유·선택하는 기능은 실제 수요를 확인한 뒤 검토한다.

## V1 제외 및 이후 계획

- V2: 고객 전용 예약페이지. 화면은 분리하되 사장님 화면과 같은 예약 데이터·충돌 규칙을 사용한다.
- 비용 관리, 엑셀 export, 전자서명, 에이전트는 V1 제외.
- 직원 개별 로그인, 개인 일정 공유, 화면 정보 숨김·재배치·크기 조절은 V1 제외.
- 커뮤니티·플랫폼 회원가입·샵 홍보·이미지 기반 스타일 탐색 에이전트는 추후 구상이며 지금 설계하지 않는다.
- 커뮤니티 구상은 사장님·종사자 중심이며 일반 고객도 방문할 수 있는 방향이다. 세부 논의는 중단한다.

## V2로 이관할 예약페이지 합의

- 고객 회원가입 없이 이름·전화번호를 받아 사장님 측 고객 기록과 매칭한다. 매칭 상세 정책은 미정이다.
- 시술·담당자 선택 → 문자 인증 → 최신 가능 시간 선택 → 서버 충돌 검사 후 예약 확정.
- 시간 임시 선점 및 기기별 인증 장기 유지는 제외한다.
- 고객 시작 시간 간격은 샵별로 5/10/15/20/25/30분 중 설정한다. 기준 시각은 미정이다.
- 기존 시작 시간 후보를 유지하고 충돌 후보만 제외한다. 사장님 예약 종료시각을 기준으로 간격을 다시 시작하지 않는다.
- 시술 길이는 간격에 맞춰 반올림하지 않는다. 자투리 시간은 허용한다.
- 고객은 예약 생성만 가능하다. 변경·취소는 샵에 문의하고 사장님이 처리한다.
- 예약 전후에 변경·취소 문의 안내와 연락 수단을 제공한다.
- 샵별 예약페이지 디자인, 시술 선택, 담당자 선택, 사장님 화면 반영·신규 예약 알림의 상세 범위는 V2에서 정한다.
- 주간 스케줄 확정 방식과 고객에게 몇 주 앞까지 예약을 열지에 대한 정책은 V2에서 정한다. 사장님·고객 화면은 서버의 같은 일정 데이터를 사용한다.

## 개발 방식과 역할

- client/: AI-first 프런트 구현. 사용자가 화면과 코드 구조를 직접 리뷰한다.
- V1 프런트 기본 스택: React + Vite + TypeScript, TanStack Router, TanStack Query, Zod, StyleX, Oxlint.
- nuqs는 제외한다. URL 상태는 TanStack Router의 search params로 관리한다.
- Zustand, TanStack Table, TanStack Form은 선설치하지 않는다. 필요한 시점에 사용자가 직접 설치하며 AI는 임의로 추가하지 않는다.
- 서버 데이터는 Query, URL에 둘 날짜·필터·페이지는 Router, 일시적인 UI·입력 상태는 로컬로 관리한다. 개인정보는 URL에 넣지 않는다.
- 패키지 매니저는 pnpm으로 확정한다.
- 프런트 프로젝트 초기 구성은 사용자가 직접 담당한다. AI는 디렉터리·모노레포 구조, 패키지 설치, 빌드·린트·포매터 설정에 대한 구성 계획·스토리·스캐폴딩을 만들지 않는다.
- 포매터(oxfmt 포함)와 StyleX 빌드·린트 연동 등 구성 선택은 사용자에게 맡긴다. AI는 사용자가 마련한 구성을 읽고 그 위에서 기능 스토리를 계획·구현한다.
- server/: 사용자가 NestJS + PostgreSQL로 직접 구현·학습한다. AI가 백엔드 구현을 대신하지 않는다.
- 서버 실행·DB 연결·마이그레이션의 최소 기반을 먼저 마련한다. 전체 테이블을 선설계하지 않는다.
- 사용자 담당 초기 기반과 프런트 구성이 준비되면, 작은 기능마다 API 요청·응답·실패 조건 합의 → 사용자 BE / AI FE 구현 → 실제 API 연결 → 리뷰 순서로 진행한다.
- 임시 목업 사용은 가능하나 실제 API 저장·조회·실패 처리 확인 없이 스토리를 완료하지 않는다.
- 고객 예약페이지와 공통 설정은 향후 모노레포 패키지로 분리할 계획이며 지금 구조를 확정하지 않는다.
- planner는 범위·스토리·계약·검증 기준을 작성한다. 사용자 승인 전 구현·executor 인계 금지.

## 다음 결정과 완료 기준

1. 카카오 알림: 전날 예약 안내의 발송 대상·시각·문구 변경 범위와 발송 시점의 최신 예약 반영·실패 처리. 제공사·템플릿 제약 확인. 생성·변경·취소 즉시 알림은 제외.
2. 매출: 실제 결제액 기준의 집계 날짜·고객별 집계, 취소·정정·환불 반영 규칙.
3. 예약: 샵/담당자 근무시간 상속 관계와 변경 시 기존 예약 보호 규칙, 반복 차단의 주기·예외·충돌 처리, 가격 변경 반영 규칙, 완료/취소 처리의 정정 규칙.

5. 계정·운영: 사장님 인증, 고객정보 보호, 데이터 백업과 운영 환경.
