# V1 스토리 인덱스

범위 기준: [v1-scope.md](v1-scope.md).
디자인 기준: [선택 시안과 공통 UI](../design/README.md). UI 작업 전 문서와 이미지를 함께 확인한다.
전체 목록은 순서·크기 검토용 초안이며 구현 승인이 아니다.
현재 작업은 [CURRENT.md](../CURRENT.md), 재개 절차는 [RESUME.md](../RESUME.md)에서 확인한다. 현재 상태·승인은 런타임 checkpoint가 정본이며 승인된 story.md는 범위로 동결한다. 과거 S001 상태는 새 런타임 승인으로 승계하지 않는다.
S001과 잔여 공통 UI(UI001~UI004)는 상세 문서가 있다. 나머지 업무 스토리는 목록 초안이며 착수 시 상세화한다.
검토 후 독립 스토리는 28개다. S021은 S020에 통합했으며 기존 참조 혼동을 피하려고 ID와 순서 번호를 재부여하지 않는다.

## 작업 단위와 역할

- 한 스토리는 확인 가능한 흐름 단위다. 공통 UI는 시안의 검토 가능한 조작 흐름을 UI001~UI004로 분리하고, 업무 기능 스토리 28개와 구분한다. 작업 순서는 FE 스캐폴딩 → FE 구조 확정 → shared/ui 공통 UI → features 업무 화면·routes 조립 → 사용자 BE 연결이다. 두 번째 feature 소비자는 공통 UI 개발의 선행 조건이 아니다.
- AI: 디자인·FE 구현. 사용자: 프로젝트 구성, BE 직접 구현, FE 구조·방식·디자인 리뷰.
- 사용자가 마련한 도구·스캐폴딩을 읽고 FE 구조를 planner에서 함께 논의·확정한다. 현재 목록은 업무 기능 기준이며 사용자 담당 서버·인프라 구성이나 임의 패키지 설치 작업을 추가하지 않는다.
- 스토리는 범위·업무 규칙·완료 조건 중심으로 작성한다. API 경로·요청/응답·오류 코드 초안은 제외한다.
- FE 목업은 중간 확인용이다. 실제 BE 연결과 사용자 리뷰 전에는 해당 스토리를 완료하지 않는다.
- 아래 의존성은 기능 기준이다. UI 프레임워크·테스트 도구·서버 상세 구조를 지정하지 않는다.
- S003 이전에는 비공개 개발 환경의 가상 데이터만 사용한다. 실고객 데이터 운영은 인증·접근 보호와 사용자 담당 운영 준비 후에만 가능하다.
- 한 번에 한 스토리만 승인·인계한다. 큰 흐름의 순서는 아래와 같고, 독립 항목은 사용자와 재배치할 수 있다.

타임테이블은 공통 화면이며 담당자별 독립 화면을 추가하지 않는다.

- 합의한 V1의 큰 기능은 모두 목록에 대응한다. 미정인 완료 처리·회원권 차감 연계는 확정 기능으로 추가하지 않았다.
- 중복 분해 제거: 잔액 차감과 입력 오류 정정은 같은 증감·사유·이력이므로 S020에 통합했다. S023은 실제 결제·매출 기록이라는 다른 대상을 다루므로 유지한다.
- S009는 첫 예약 등록과 오늘 일정 확인을 잇는 최소 흐름이다. 여러 시술·다른 날짜·변경·취소를 포함하지 않는다. 다른 스토리에서도 예약 입력에 필요한 기존 고객 선택을 제공하되 별도 CRM 검색 기능으로 확장하지 않는다.
- S017(반복 차단), S024(해지 환불), S028(자동 안내)은 상세화 시 크기를 다시 확인한다. 반복 예외·환불 정책 계산·메시지 종류 확대를 지금 추가하지 않는다.
- S027은 외부 발송 연동과 테스트 수신, S028은 예약에 따른 자동 발송으로 나눠 각각 검증한다. 기존 실제 고객에게 테스트 메시지를 보내지 않는다.
- 인증·접근 보호는 실고객 데이터 사용의 선행 조건이다. 프로젝트 구성·운영 준비가 이 목록 밖이라고 해서 생략하는 것이 아니다.
- 테마는 S029에서 사용자 변경 기능을 제공한다. 앞선 FE 구현도 합의한 StyleX 방식으로 작성하되, 디자인 시스템·공통 프레임워크 구축 스토리를 추가하지 않는다.
