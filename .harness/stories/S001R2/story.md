# S001 — 고객 등록 → 목록 확인 (실행 revision S001R2)

## 목적·문서 관계

사장님이 고객 이름·전화번호를 등록하고 목록에서 확인한다. 화면·사용자 직접 BE 구현·실제 연결을 **하나의 업무 스토리 S001**로 관리한다. FE 목업 완료를 별도 기능 완료로 세지 않는다.

기존 [S001/story.md](../S001/story.md)는 공통 UI 1단계의 승인 이력으로 수정하지 않는다. 본 문서는 같은 기능의 후속 실행 revision이며 하네스 ID만 `S001R2`다. 업무 스토리 총수·S002 이후 의존성은 바꾸지 않는다. 과거 S001의 REVIEW_DECISION·리뷰 envelope를 새 승인으로 복원하거나 이어 쓰지 않는다. 현재 공통 UI 기반은 사용자 확인이 끝난 UI001~UI004 및 기존 Button/Field/Input이다.

## 사용자 합의·이번 승인 경계

사용자는 첫 고객 관리 화면을 임시 UI 조각이 아니라 해당 기능을 실제로 검토할 수 있는 완성된 화면으로 먼저 만들기로 했다. FE는 executor → reviewer → 사용자 확인, BE는 사용자가 직접 구현하며 필요할 때 가이드·검토를 요청한다. 실제 연결 뒤 전체 완료한다.

**이번 handoff는 아래 A(FE 화면·가상 동작)만 승인한다.** B(BE 직접 구현)·C(실제 연결)는 전체 완료 조건을 이해하기 위한 후속 단계이며 executor의 서버 작업·API 연결·설치 권한을 주지 않는다. 승인 후 본 문서는 동결한다. 후속 구체 범위·사용자 결정·승인 근거는 implementation.md에 추가하고 필요한 재승인을 받는다.

## A. 이번 실행 범위 — 고객 관리 화면 완성

### 화면·배치

- 확정 경로 `/customers`. `routes/customers.tsx`는 페이지 조립만, 업무 UI·입력·상태는 `features/customers/`에 둔다. [기존 구조](../S001/fe-structure.md)의 의존 방향과 [현재 공통 UI 파일 배치](../ui-structure.md)를 따른다.
- [잉크 블루 시안](../../design/images/02-ink-blue.png)의 좁은 레일·상단 영역·밀도 있는 고객 목록·우측 등록 영역을 기준으로 완성된 고객 화면을 만든다. 레일은 현재 고객 항목만 실제 링크로 제공한다. 예약·매출·설정의 가짜 링크나 미구현 업무 화면은 만들지 않는다. 공통 앱 shell 프레임워크를 미리 추출하지 않는다.
- 고객 수·이름·전화번호 표, 등록 열기/닫기·취소·저장. 식별자는 내부 key로 쓰고 행 번호는 식별자가 아니다. 고객 상세·행 선택 기능은 없다.
- 데스크톱은 목록과 비모달 등록 패널을 함께 조작한다. 좁은 화면은 같은 페이지에서 등록 영역을 위·목록을 아래로 쌓는다. Drawer나 별도 모바일 화면을 만들지 않는다.
- 초기에는 목록과 등록 진입 버튼을 보여준다. 등록을 열면 이름 입력으로, 취소/닫기 후에는 등록 진입 버튼으로 포커스를 보낸다. 취소는 입력을 버리고 닫으며 재열기 시 빈 폼이다. 저장 중에는 입력·취소/닫기와 중복 제출을 막고 진행을 알린다.
- 기존 `/` 공통 UI 검토 화면과 01~08 예시는 유지한다. `/customers`로 가는 최소 링크만 추가한다. `/` 리다이렉트·검토 route 이전/삭제는 제외한다.
- 가상 데이터·저장 미연결 안내를 화면에 명시한다. 로그인된 사용자/샵의 실제 인증을 구현한 것처럼 표시하지 않는다. 실고객 정보를 입력하지 않도록 안내한다.

### 동작·상태

- 이름·전화번호 필수. 문자열로 관리해 전화번호 앞자리 0을 보존한다. 이름 앞뒤 공백 제거·공백뿐인 이름 거절을 적용한다. 전화번호는 검토용 숫자·공백·하이픈 입력만 허용하고 비교 시 공백·하이픈을 제거한다. 국가번호·통신사·자릿수 세부 정책은 실제 BE 연결 전에 사용자와 맞춘다. 목업 규칙을 서버 규약으로 강제하지 않는다.
- 가상 고객 식별자로 동명이인을 구분한다. 초기 예시 목록은 가상 데이터만 사용한다. 등록 성공이면 새 고객을 목록 맨 위에 한 번 반영하고 수를 갱신한다. 폼은 초기화·닫기, 등록 진입 버튼으로 복귀한다.
- 중복 확인은 등록 실행 결과로만 처리한다. 입력·blur 중복 조회 없음. 가상 저장 결과에서 같은 비교 번호면 중복 오류를 전화번호 Field에 연결하고 입력을 유지한다. 첫 오류 입력에 포커스를 보낸다.
- 저장 실패는 입력을 유지하며 성공 안내·목록 추가를 하지 않는다. 재시도는 사용자가 다시 저장하는 동작이다. 자동 재시도 없음.
- 조회 로딩·빈 목록·조회 실패·정상 목록을 구분한다. 실패 시 재시도로 로딩을 거쳐 가상 목록을 보여준다. 조회 실패를 0명으로 표현하지 않는다.
- Button/Field/Input/Table/EmptyState/Skeleton/ErrorState/LiveNotice 등을 직접 재사용한다. 처리 결과는 인라인 LiveNotice 하나로 알린다. 매 표시 사건에 `noticeKey`를 바꿔 같은 실패 재발도 구분한다. Field는 구체 오류, 결과 알림은 요약으로 역할을 나눠 같은 문장을 중복 live 영역에 넣지 않는다. Toast는 불필요하므로 추가하지 않는다.
- 작은 ‘가상 동작 확인’ 영역에서 다음 조회/저장의 성공·실패·빈 결과를 재현한다. 실제 목록/폼을 같은 경로로 조작하고 별도 데모 앱·상태 카탈로그를 만들지 않는다. 오류는 고객 이름 같은 입력 마법값으로 유발하지 않는다.
- 데이터는 페이지 인스턴스의 로컬 메모리만 사용한다. 새로고침/페이지 이탈 시 초기 예시로 돌아간다. localStorage/전역 SSR 공유 배열/실제 fetch 없음. 가상 동작과 데이터는 customers 내부에 모아 이후 교체 범위를 드러내되 repository interface·provider·DI framework는 만들지 않는다.
- 가상 비동기 대기는 짧게 두고 처리 중 중복 요청·페이지 이탈 뒤 늦은 반영을 막는다. UI004 검토 전용 util을 feature에서 import하지 않는다. 필요 로직만 feature 내부에 둔다.

### 파일 경계

- `client/src/features/customers/`: `customers-page.tsx`, `customer-form.tsx`, `customer-list.tsx` 및 실제 필요한 가상 데이터·검증·상태 로직/테스트. 작은 책임은 억지로 hooks/util 파일로 쪼개지 않는다. 소문자 파일명·직접 경로 import.
- `client/src/routes/customers.tsx`, 기존 `routes/index.tsx`의 진입 링크. `routeTree.gen.ts`는 기존 생성 도구로 갱신하고 직접 편집하지 않는다. 라우트 추가에 따른 생성물 변경을 기록한다.
- 기존 StyleX 의미 토큰·공통 컴포넌트 API·CSS 진입점·설정은 유지한다. 새 화면 스타일은 feature 소유다. 부족한 공통 API 발견 시 임의 확대하지 말고 사용자에게 최소 보완안을 제시한다.

## B. 사용자 직접 BE 구현 — 후속 단계

FE 화면 확인 후 planner는 화면 행동을 다음 도메인 과제·검증 기준에 연결해 가이드한다. 서버 코드를 대신 쓰거나 정답 테이블/API를 먼저 고정하지 않는다.

- 고객 식별·이름/전화번호 저장·샵 범위의 고객 목록 조회.
- 서버 필수값/전화번호 검증 및 정규화 정책 확정. 클라이언트 검증은 서버 검증을 대신하지 않는다.
- 같은 샵의 동일 전화번호 중복 방지. 동시 요청에서도 최대 한 기록만 생성되도록 데이터 무결성 검증.
- 저장·검증·중복·조회 실패를 소비자가 구분할 수 있는 결과.
- 서버 재조회·새로고침 후 같은 고객 식별자와 데이터 유지.

사용자는 설계·구현을 직접 하고 필요할 때 힌트/코드 검토를 요청한다. 자동 executor → reviewer 적용 대상이 아니다. API 경로·요청/응답·오류 코드·테이블/마이그레이션 초안은 이번 문서에서 지정하지 않는다. BE 준비 전에는 비공개 개발 환경·가상 데이터만 사용한다. 실고객 운영은 인증·샵 접근 보호 준비 후에만 가능하다.

## C. 실제 연결 — 별도 승인 후

사용자가 준비한 서버 규약·실행 방법·검증 근거를 읽고 FE 가상 동작을 실제 요청으로 교체한다. 연결 범위·오류 대응·비밀 제외 환경 설정을 먼저 합의한다. 실제 연동·필수 게이트·사용자 최종 확인 전에는 S001을 완료하지 않는다.

## 제외 범위

고객 수정·삭제·상세·검색·필터·페이지네이션·가져오기/내보내기, 예약·회원권·매출·로그인 구현, 전체 메뉴/앱 shell framework·테마 선택, 새 Query/Form/Table/상태 라이브러리·패키지 설치·설정 변경, AI의 server/·DB 구현, FE 단계의 API 연결·영속 저장, 커밋·푸시. 긴 목록 규모 대응은 실제 BE 조회 방식과 함께 별도 결정하며 이번 목업 때문에 설계하지 않는다.

## 완료 조건

### A 단계 확인 기준 — 전체 DONE 아님

1. `/customers` 직접 진입·새로고침 및 `/` 링크로 접근 가능하다. 시안 방향의 완성된 고객 화면을 데스크톱·375px에서 조작하며 페이지 가로 넘침이 없다. 기존 `/` 검토 화면 유지.
2. 등록 열기 → 이름/전화번호 입력 → 가상 저장 성공 시 목록과 고객 수가 한 번 갱신되고 폼 초기화·닫힘·포커스 복귀·성공 안내가 동작한다. 동일 이름 고객도 식별자로 구분한다.
3. 필수값·허용 문자·중복 번호 오류는 적절한 Field에 연결되고 입력을 유지한다. 전화번호 앞자리 0 보존, 입력/blur 중복 확인 없음.
4. 저장 중 재제출/닫기를 막는다. 저장 실패 시 목록을 바꾸지 않고 입력·오류를 유지한다. 같은 실패를 반복해도 동적 결과가 갱신된다.
5. 조회 로딩/빈 결과/실패/정상 목록이 구분되고 조회 실패 후 재시도 가능하다. 실패를 빈 목록으로 표시하지 않는다. 늦은 가상 완료가 새 상태나 이탈한 화면을 덮지 않는다.
6. 키보드·보이는 포커스·label/설명/오류·busy 연결, 등록 열기/취소/성공/오류 포커스 동작을 확인한다. 모바일 등록/목록·긴 이름/문구도 읽고 조작할 수 있다.
7. 가상 데이터 안내가 보이고 새로고침하면 초기 예시로 복귀한다. 서버 요청·브라우저 영속 저장·shared→feature 의존이 없으며 기존 공통 UI 테스트·조작에 회귀가 없다.
8. 고정 기준 FE 코드 리뷰·사용자 화면/구조 확인 후 결과를 ‘FE 단계 확인 완료’로 기록한다. 실제 저장·새로고침 영속성을 통과했다고 하지 않는다.

### S001 전체 완료 조건 — 기존 게이트 상속

- 유효 등록은 서버 식별자 발급·DB 저장 후 목록에서 확인하며 새로고침 후 동일 기록 유지.
- 서버 필수값/합의한 전화번호 검증 실패 시 저장하지 않고 화면에 안내.
- 같은 샵의 동일 전화번호·동시 등록 요청에서 추가 중복 저장 없음. 입력·blur 사전 중복 API 없음.
- 실제 저장·조회 실패를 성공/빈 목록과 구분하며 입력 보존·재시도 가능.
- 사용자 BE 검증 근거와 실제 연결 QA·고정 기준 리뷰·사용자 화면/코드/통합 확인 완료. 실고객 사용의 인증·접근 보호 조건 유지.
- 기존 필수 `deep-guide.md`, `eli5.md`, `quiz.md`는 이 스토리에 상속한다. 실제 구현을 근거로 planner가 작성하고 사용자 학습 확인을 받는다. FE 문서만으로 BE 학습·통합 검증을 완료 처리하지 않는다.

## 진행·인계·대기

1. 이번 handoff → A 구현/QA → 고정 기준 리뷰 → 사용자 선택 수정/확인. 리뷰 요청에는 **A의 기준만 검토하며 전체 S001 DONE은 아님**을 명시한다.
2. FE 확인을 전체 ‘스토리 종료’로 처리하지 않는다. 미해결 B/C·학습 게이트 때문에 done 명령을 실행하지 않고, FE 사용자 확인과 BE 준비 사항을 implementation.md에 기록한다.
3. 열린 리뷰·typed 결과를 정상 처리한 뒤 `checkpoint S001R2 blocked --note 'FE 사용자 확인 완료; 사용자 직접 BE 구현·실제 연결·학습 게이트 대기. 소스 변경 승인 아님'`으로 대기한다. blocked는 결함 확정이 아니라 외부 의존성 대기다. 대기 중 새 기능 스토리 자동 착수 없음.
4. BE 가이드는 사용자가 요청하면 planner가 제공한다. BE 변경은 사용자 직접 수행하며 실행자 자동 수정·자동 리뷰는 없다. 열린 frozen 리뷰 중에는 소스 변경하지 않는다.
5. BE 준비 후 resume·기존 리뷰/소스 기준을 재검증한다. blocked 해제·FE 연결에는 별도 명시 승인 필요. 서버 변경을 과거 FE baseline의 검증으로 취급하지 않는다. 현 하네스의 리뷰 이후 전이/소스 지문 제약 때문에 재개가 막히면 사용자에게 알리고 멈춘다. checkpoint/승인/보고서 직접 수정이나 가짜 done으로 우회하지 않는다. 후속 연결의 정확한 승인·기준 갱신 절차는 그 시점에 확인한다.
6. 최종 통합·상속 학습·사용자 최종 확인까지 끝난 경우에만 전체 done. 코드리뷰/Fix·executor QA/Fix 각각 최대 3회, 같은 실패 연속 2회면 blocked. 사용자 BE 학습 과정을 AI 수정 횟수로 임의 계산하지 않는다.
