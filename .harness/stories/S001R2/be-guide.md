# S001 BE 직접 구현 가이드 — 고객 등록·목록 조회

## 이 문서로 할 일

**목표: 지금 보이는 고객 화면의 ‘등록’과 ‘조회’를 실제 PostgreSQL 저장·조회로 바꿀 준비를 한다.** 서버는 직접 구현한다. 이 가이드는 구현 순서·판단 기준·검증 과제이며 복사할 정답 코드나 확정 API 명세가 아니다.

- 업무 범위 정본: [story.md](story.md)의 B/C·전체 완료 조건. 승인된 story.md는 수정하지 않는다.
- 현재 상태: A(FE) 사용자 확인 완료, `S001R2 / blocked`는 사용자 BE·연결·학습 대기다. 결함 확정이나 전체 DONE이 아니다.
- 담당: 사용자 = 서버 설계·설치·구현·검증. planner = 가이드·질문/설계 논의. FE 실제 연결 = BE 준비 후 별도 승인받은 executor 작업.
- 이번에는 등록·목록만 만든다. 수정·삭제·검색·페이지네이션·로그인·회원권·예약 API는 만들지 않는다.
- 인증 준비 전에는 로컬/비공개 개발 환경에서 **가상 데이터만** 사용한다. 개발용 샵 고정은 인증·권한 구현을 대신하지 않는다.
- 이 문서 작성은 서버·FE 수정, 의존성 설치, blocked 해제, 커밋·푸시 승인이 아니다. AI는 실행하지 않는다.

## 1. 화면을 BE 동작으로 읽기

| 화면에서 하는 일 | BE가 책임질 일 | BE가 하지 않아도 되는 일 |
| --- | --- | --- |
| 고객 페이지 열기·다시 조회 | 현재 샵 고객을 안정된 순서로 조회 | Skeleton·포커스·로딩 시간을 만들기 |
| 고객 저장 | 입력 검증 → 전화번호 비교 형태 정리 → DB 저장 → 저장 결과 반환 | 패널 닫기·성공 알림 표시 |
| 이미 있는 번호로 저장 | 같은 샵의 중복임을 구별 가능한 결과로 전달 | blur 시 사전 중복 확인 API 제공 |
| 고객이 없음 | 조회 성공이지만 결과가 없음을 전달 | 실패를 빈 목록으로 바꾸기 |
| 저장/조회 중 문제 발생 | 실패 종류를 구분하고 내부 정보는 숨기기 | FE 입력값·선택 상태를 서버에 저장하기 |
| 화면 새로고침 | 이전에 저장한 동일 식별자의 고객 조회 | 매번 예시 고객으로 초기화하기 |

BE가 만들어야 할 것은 UI 컴포넌트별 API가 아니라 **고객 등록과 고객 목록 조회 두 동작**이다. 취소/닫기 버튼에는 서버 작업이 없다.

### 현재 FE에서 참고할 코드

모든 경로는 프로젝트 루트 기준이다.

- `client/src/features/customers/customer.ts`: 화면에 필요한 고객 정보는 `id`, `name`, `phone`. 이름 trim, 번호의 숫자/공백/하이픈 허용, 공백·하이픈 제거 비교는 현재 **목업 규칙**이다. 국가번호·자릿수 정책은 미확정이다.
- `customer-form.tsx`: 입력 유지·필드 오류·중복 안내를 맡는다. 서버 검증 오류를 연결하는 방식은 후속 FE 연결에서 보완한다.
- `customer-mock.ts`: 조회의 loaded/failed, 저장의 saved/duplicate/failed 분기를 이해하는 자료다. 이 union을 HTTP 응답 형식으로 복사할 필요는 없다.
- `use-customer-mock.ts`: 실제 연결 시 교체할 가상 요청·상태 처리 위치다. 저장 성공 후 늦은 조회가 목록을 덮지 않게 한 FE 수정도 유지해야 한다.
- **복사하면 안 되는 목업 동작:** 600ms 인위적 지연, 빈 결과 선택 시 저장소 초기화, `c-1001` 같은 가상 ID, 실패 선택 컨트롤. 실제 조회는 데이터를 삭제하지 않는다.

## 2. 출발점 확인

작성 시 실제 파일을 읽은 결과이며 서버 실행·테스트 결과는 아니다.

| 확인 파일 | 현재 상태 |
| --- | --- |
| `server/package.json` | NestJS 12·Vitest 4·Supertest. PostgreSQL 드라이버/ORM·검증 라이브러리는 직접 dependency에 없음 |
| `server/src/main.ts` | AppModule 생성 후 `PORT` 또는 3000에서 실행. 전역 입력 검증 구성 없음 |
| `server/src/app.module.ts` | AppController/AppService만 등록. 고객 모듈·DB 연결 없음 |
| `server/src/app.controller.ts`, `app.service.ts` | 기본 GET → Hello World |
| `server/src/app.controller.spec.ts` | 기본 컨트롤러 테스트 |
| `server/test/app.e2e-spec.ts` | 테스트 앱 생성·기본 HTTP 확인·종료 |
| `server/tsconfig.json` | ESM/NodeNext. 현재 서버 내부 import는 `.js` 확장자 사용 |

`server/AGENTS.md`·`CLAUDE.md`는 현재 찾지 못했다. 서버에 별도 지침을 추가하면 그 지침을 우선 읽는다. FE의 타입/도구 규칙을 서버에 자동 적용하지 않는다.

사용자가 이미 외부 DB를 준비했는지는 파일만으로 알 수 없다. 연결 정보가 있다면 재설치보다 기존 구성을 먼저 확인한다. 비밀번호·실제 고객 데이터는 문서나 대화에 올리지 않는다.

## 3. 시작 전 결정할 것 — 한 번에 네 가지

아래는 **권고와 미정 사항**이다. 직접 선택한 뒤 문서 끝 결정 기록에 남긴다. 여러 라이브러리를 비교하느라 전체 작업을 멈출 필요는 없다.

| 결정 | 이번 기능의 판단 기준 |
| --- | --- |
| DB 접근 방식 | PostgreSQL은 기존 방향. SQL을 직접 배우려면 드라이버+파라미터 SQL, 이미 익숙하거나 배우려는 ORM이 있으면 그것 하나. DB 연결·마이그레이션·테스트를 설명할 수 있는 쪽 선택. planner는 설치하지 않음 |
| 개발용 샵 범위 | 인증 전에는 서버가 정한 테스트 샵 컨텍스트로 제한하는 방식 권장. 요청 body/query의 임의 shop 식별자를 권한 근거로 믿지 않음. 실제 인증 연결 시 컨텍스트 교체 필요 |
| 입력 정책 | 이름의 공백 처리·최대 길이, 전화번호의 허용 대상/자릿수/최대 길이·정규화·표시 형식. 국내 휴대폰만 받을지 유선/국제번호도 받을지 먼저 정하기. 현재 FE의 느슨한 목업 검증을 최종 정책으로 간주하지 않음 |
| 저장 정보·정렬 | 고객 고유 ID, 소속 샵, 이름, 비교용 전화번호, 등록 순서 판단 근거가 필요. ID 형식·실제 컬럼명·원본 번호 보존 여부는 직접 결정. 신규 고객이 위로 오고 동률에도 순서가 일정해야 함 |

**첫 착수 지점:** DB 접근 방식과 테스트 DB 준비 여부부터 정한다. 이미 선택했으면 그 결과를 기록하고 0단계로 간다. API 경로·JSON 필드·HTTP 오류 코드는 아래 3단계에서 실제 서버 규약으로 정한다.

## 4. 구현 순서 — 단계별로 끝내기

### 0단계 · 기존 서버 실행과 테스트 DB 연결

**목표:** 기능 코드 전, 기존 서버와 선택한 PostgreSQL 접근 방법이 동작함을 확인한다.

할 일:
1. 기존 build/test/서버 실행 결과를 먼저 기록한다. 설치가 필요한지는 사용자가 판단한다.
2. 개발용 DB와 테스트용 DB를 구분한다. 테스트 정리 작업이 개발/운영 DB를 건드리지 않게 연결 대상을 확인한다.
3. 선택한 도구로 DB에 연결해 읽기 전용 간단한 쿼리가 성공하는지 확인한다. 연결 실패도 식별한다.
4. DB 클라이언트 생성·종료 위치를 정한다. 요청마다 연결을 무한 생성하거나 테스트 프로세스를 열린 연결 때문에 남기지 않는다.

완료 확인: 기존 서버 응답·build/test 실제 결과, DB 연결 성공/실패 확인을 적을 수 있다. 아직 고객 기능 완료는 아니다.

### 1단계 · 고객 정보와 데이터 무결성 만들기

**목표:** 한 고객을 저장할 정보와 ‘저장되면 안 되는 값’을 DB에 표현한다.

할 일:
1. 고객 식별자·소속 샵·이름·번호 비교값·정렬 근거를 저장할 모델을 작성한다. 화면 행 번호를 PK로 쓰지 않는다.
2. 전화번호는 숫자가 아니라 문자열로 다룬다. `010…`의 앞자리 0은 정보다.
3. 같은 샵의 같은 비교 번호가 두 번 저장되지 않도록 **DB 유일성 제약**을 둔다. 개념은 `(샵, 정규화된 전화번호)`의 유일성이다. 번호 하나만 전역 unique로 만들면 다른 샵의 같은 고객까지 막는다.
4. 필수값 null 방지·선택한 길이 제한을 맞춘다. 입력 경계의 공백/타입 검증과 DB 제약은 서로 대신하지 않는다.
5. 선택한 도구의 마이그레이션으로 재현 가능한 변경을 남긴다. 콘솔에서만 수동 변경해 끝내지 않는다. 테스트 샵이 필요하면 최소 fixture로 준비하되 샵 관리 기능까지 만들지 않는다.

완료 확인: 빈 **테스트 DB**에 적용 가능, 유효 행 저장 가능, 같은 샵·같은 비교 번호의 두 번째 행 거절, 다른 샵의 같은 번호는 별도 고객으로 저장 가능. 이 테스트는 인증 완료 증거가 아니다.

생각할 질문: `같은 이름 + 다른 전화번호`가 왜 허용되어야 할까? 번호가 같아도 샵이 다르면 왜 별도 기록일까?

### 2단계 · 등록 한 건을 DB까지 관통시키기

**목표:** 허용된 입력만 저장하고 DB가 확정한 결과를 돌려준다.

할 일:
1. 요청 입력을 신뢰하지 않는다. body 누락/null/배열, 숫자나 객체로 온 이름·전화번호 등을 문자열 처리 전에 거절한다. TypeScript 타입 선언만으로 런타임 검증이 생기지 않는다.
2. 결정한 이름·전화번호 검증/정규화를 적용한다. 잘못된 문자를 무작정 전부 지워 다른 유효 번호로 바꾸지 않는다. 허용한 구분자만 제거하고 비교한다.
3. 샵 컨텍스트는 서버가 정한 신뢰 경로에서 받는다. body에 임의 ID·샵 필드가 있어도 그대로 DB 모델에 펼쳐 저장하지 않는다. 허용 필드만 선택한다.
4. 저장 성공 응답은 실제 쓰기가 완료된 뒤 반환한다. DB ID·저장된 값을 근거로 응답하고 FE가 만든 임시 ID를 권위 있는 식별자로 쓰지 않는다.
5. 전화번호 중복 유일성 위반만 중복 결과로 변환한다. 다른 DB 제약 오류나 연결 오류를 전부 ‘중복 번호’로 잡지 않는다.

완료 확인: 유효 고객 1건 생성, 서버 검증 실패는 0건, 중복 재등록은 총 1건 유지, 앞자리 0·동명이인 유지. 문자열 연결 SQL 대신 파라미터 바인딩 또는 선택한 ORM의 안전한 바인딩을 사용한다.

핵심: `조회해서 없으면 INSERT`만으로 중복이 막히지 않는다. 두 요청이 동시에 ‘없음’을 확인할 수 있기 때문에 마지막 방어선은 DB 제약이다. 사전 조회를 하더라도 제약 위반 처리는 필요하다.

### 3단계 · 등록·목록을 HTTP로 제공하기

**목표:** FE 없이 HTTP 클라이언트/자동 테스트로 등록과 목록을 사용한다.

추천 책임 구분(파일 이름·개수는 강제 아님):
- Controller: HTTP 입력·결과 변환. 폼 UI나 SQL 세부를 모두 몰아넣지 않는다.
- Service: 등록/목록 흐름·샵 범위·업무 실패 구분.
- DB 접근: 선택한 드라이버/ORM의 쿼리·연결. 구현 하나를 위해 별도 repository interface/추상 클래스/범용 CRUD 계층부터 만들지 않는다.
- Module: 필요한 controller/provider를 연결. app 기본 파일은 기존 Nest 구성 참고용이다.

할 일:
1. 등록·목록 두 동작의 경로·요청·응답·오류 규약을 직접 정하고 테스트에 사용한다. 여기서는 임의 API 초안을 고정하지 않는다.
2. 목록은 항상 해당 샵 조건으로 조회한다. 최신 등록 우선과 안정적 동률 정렬을 적용한다. 화면의 01/02·고객 수는 이번 전체 목록에서 FE가 계산할 수 있어 별도 API가 필요 없다.
3. 조회 성공 0건과 조회 실패를 구분한다. catch 후 빈 배열 반환은 금지한다.
4. 등록 응답에서 저장된 고객을 식별할 수 있게 한다. 검증 실패는 관련 필드를, 중복은 번호 중복임을 FE가 구별 가능하게 한다. 정확한 상태 코드·JSON 구조는 직접 정한다.
5. 런타임 검증 구성은 실제 요청 경로에 적용한다. 테스트 앱도 같은 필수 검증을 사용해야 한다. `main.ts`만 고치고 테스트 앱에서 빠뜨리지 않는다.

완료 확인: HTTP로 등록 → 목록 조회 → 같은 ID/값 확인. 서버 프로세스 재시작 후 재조회해도 유지. 다른 샵 데이터가 목록에 섞이지 않음. FE 아직 미연결이어도 여기까지 독립 검증 가능하다.

### 4단계 · 실패와 동시성 확인

**목표:** 성공 한 번보다 중요한 경계에서 데이터가 깨지지 않음을 입증한다.

| 시나리오 | 기대 결과 |
| --- | --- |
| 이름 누락/공백, 번호 누락/허용하지 않은 값 | 검증 실패, DB 추가 없음 |
| 문자열 대신 숫자/null/배열/객체 | 서버 오류로 터지지 않고 입력 거절 |
| 동일 샵의 번호 표기만 다른 두 입력 | 합의한 정규화에 따라 같은 번호면 중복, 총 1건 |
| 동일 이름·서로 다른 번호 | 서로 다른 ID로 2명 저장 |
| 같은 샵·같은 번호로 동시 등록 | 깨끗한 테스트 데이터 기준 정확히 한 건 생성, 나머지는 구별 가능한 중복 결과 |
| 두 테스트 샵에서 같은 번호 | 각 샵의 고객으로 저장, 목록에는 자기 샵 것만 조회 |
| body의 다른 샵 ID·임의 고객 ID | 서버가 정한 소유 범위/식별자를 덮어쓰지 못함 |
| 조회 DB 연결 실패 | 실패 결과, 성공 0건으로 응답하지 않음 |
| 쓰기 전 DB 장애/명확한 저장 실패 | 성공 결과 없음, 해당 테스트에서 추가 행 없음 |
| 쓰기 확정 뒤 응답 유실·클라이언트 연결 종료 | 저장됐을 수도 있음. 요청 실패를 ‘DB 미저장’으로 단정하지 않고 재조회로 확인 |
| 빈 목록 | 정상 조회 결과 0건. 기존 고객을 삭제하지 않음 |
| 프로세스 재시작 후 조회 | 동일 ID·값 유지, 중복 제약도 유지 |

동시성 검증은 실제 PostgreSQL을 대상으로 여러 요청을 병렬로 보내고 응답뿐 아니라 최종 행 수도 확인한다. 순차 두 번 호출·메모리 mock 테스트는 DB 경쟁 조건 검증이 아니다. 전역 JS 잠금이나 자동 고객 병합으로 해결하지 않는다.

오류 응답에 SQL·스택·접속 주소/비밀번호·다른 고객 정보를 넣지 않는다. 진단 로그에도 원본 요청/전화번호 전체를 무조건 출력하지 않는다. 장애 실험은 테스트 DB/테스트 설정에서만 한다.

## 5. 실행할 검사와 결과 기록

아래는 `server/package.json`에 존재하는 script 기준이다. **프로젝트 루트에서 사용자가 실행**한다. 이번 문서 작성 중에는 실행하지 않았다.

```bash
pnpm --dir server run build
pnpm --dir server run lint
pnpm --dir server run test
pnpm --dir server run test:e2e
```

개발 서버: `pnpm --dir server run start:dev`. `server/src/main.ts`의 기본 포트는 3000이므로 다른 앱과 겹치면 사용자가 `PORT`를 정한다. 실제 바인딩 주소/네트워크 접근을 확인하고 인증 없는 서버를 외부에 노출하지 않는다.

- 순수 검증/정규화는 unit test, HTTP 결과는 현재 Supertest 패턴, 실제 DB 제약·동시성은 분리된 테스트 DB로 확인한다.
- 테스트 시작/종료 때 자기 fixture만 정리한다. 실제 데이터가 든 DB에서 전체 삭제/초기화하지 않는다. DB 연결과 Nest 앱을 종료한다.
- `test:cov` script는 있지만 현재 coverage 결과·합의 임계값을 확인한 것은 아니다. 필요할 때 측정하며 기존 미해결 게이트를 PASS/면제로 바꾸지 않는다.
- 테스트 실행이 decorator/DI/ESM 구성에서 막히면 본 기능 결함과 도구 구성을 분리해 기록한다. 지금 파일을 읽었다는 사실이 Nest 테스트 호환성의 실행 증거는 아니다.
- 성공 출력만 남기지 말고 명령·결과·DB 사용 여부·미실행 이유를 기록한다.

## 6. BE 완료 후 FE 연결로 넘길 것

다음 정보를 이 문서 끝에 작성하거나 별도 서버 문서 경로로 전달한다. 비밀값은 제외한다.

- 결정한 입력/전화번호 정책과 DB 무결성 규칙, 구현 파일 위치.
- 등록·목록의 실제 경로/메서드·요청/응답 예시, 검증·중복·예상하지 못한 실패 구별 방식.
- 개발 서버 실행 방법·주소/포트, 테스트 DB 준비·마이그레이션 실행 방법, 필요한 환경변수 **이름만**.
- 개발용 샵 컨텍스트가 정해지는 위치와 인증 미구현 경계.
- 위 검증 명령 결과와 동시 요청/재시작 후 영속성 확인 근거.

이후 planner/executor는 별도 승인으로 가상 요청을 실제 요청에 연결한다. FE의 서버 필드 오류 처리·정규화 표시·실제 네트워크 실패·저장 후 재조회 경쟁도 맞춘다. FE와 BE origin이 다르면 CORS/프록시 방식은 실제 연결 전에 결정하며, CORS를 접근 제어로 취급하지 않는다.

**BE 준비 완료 ≠ S001 전체 완료.** 실제 화면 등록 → 목록 → 브라우저 새로고침 → 실패/중복 확인, 사용자 최종 확인과 상속 학습 게이트가 남는다. 실제 API 연결·상태 재개는 이전 FE 승인으로 자동 진행하지 않는다.

보류 유지: 디자인 디테일·등록 모달 전환·feature 폴더 재배치·MSW. BE를 만들다가 해당 FE 정리를 동시에 시작하지 않는다.

## 7. 내 결정·진행 기록

체크는 직접 구현·검증한 뒤 한다. 가이드 작성 시 전부 미실행이다.

- DB 접근 방식/선택 이유: 미정
- 개발/테스트 DB 준비 방법(비밀 제외): 미정
- 개발용 샵 컨텍스트: 미정
- 이름/전화번호 허용 범위·길이·정규화·표시 정책: 미정
- ID·정렬·중복 제약·마이그레이션 위치: 미정
- 실제 API 규약 문서/구현 위치: 미정
- [ ] 0단계 — 기존 서버 기준선·테스트 DB 연결 확인
- [ ] 1단계 — 모델·마이그레이션·샵별 번호 유일성 확인
- [ ] 2단계 — 검증된 등록과 실제 저장 결과 확인
- [ ] 3단계 — HTTP 등록·목록·재시작 후 재조회 확인
- [ ] 4단계 — 실제 DB 동시성·실패·샵 범위 확인
- [ ] 명령/실제 결과/미실행 항목 기록 및 FE 연결 자료 전달

막히면 **진행 단계·기대한 결과·실제 오류·관련 코드/테스트**를 보내면 된다. 먼저 판단 기준/힌트로 검토하고, 서버 구현은 계속 직접 한다.

첫 목표는 **테스트 DB 연결 후, 유효 고객 한 명을 저장하고 같은 ID로 다시 읽는 것**이다. 전체 BE를 한 번에 완성하려 하지 않는다.
