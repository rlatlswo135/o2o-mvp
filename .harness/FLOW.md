# 명령 기반 협업

이 계약은 `c2h init --flow`로 설치한다. planner=Pi, executor=Claude Code, reviewer=Pi.
같은 프로젝트에서 reviewer 세션은 하나만 운영한다. 모델 API 호출·새 에이전트 자동 실행·tmux 키 입력 주입은 없다.
권한·신뢰 확인은 각 CLI에 맡기며 기존 프로젝트 지침을 우회하지 않는다.

## 명령과 승인

| 위치 | 명령 | 의미 |
| --- | --- | --- |
| Pi planner | `/plan [요구사항]` | 계획 작성 → 인계 / 보강 / 논의 선택. 구현하지 않음 |
| Claude executor | `/executor` | 스토리 선택 UI → 사용자가 고른 스토리 하나만 구현 |
| Claude executor | `/harness-review [ID]` | 구현 기준 고정·리뷰 요청·회신 대기 |
| Pi reviewer | `/reviewer` | 수동 시작 또는 중단된 리뷰 수신 재시도 |
| Claude executor | `/accept` | 수정안 다중 선택 UI → 선택한 수정안만 실행 |
| Claude executor | `/feedback` | 항목 선택 UI → 의견 입력·재논의. 소스 수정하지 않음 |

Claude의 내장 `/review`는 이 흐름과 다르다. 그 명령을 덮어쓰지 않는다.
명령은 현재 세션에서 동작한다. 준비된 planner 인계가 없는 `/executor`는 계획을 추측하거나 승인하지 않는다.
일반 "작업 진행"과 `/harness-resume`은 구현 승인이 아니다. 커밋·푸시·계획 밖 설치는 별도 승인이다.

## 계획 완료 선택

스토리 작성·저장 후 planner는 `c2h_plan_next` 도구로 Pi 선택 UI를 연다.

1. **실행자에게 넘기기 (`handoff`)**: 선택 후 스토리·범위·선행 조건·다른 활성 작업을 다시 확인한다.
   미결정·미준비면 인계하지 않고 이유를 알린다. 준비된 스토리와 인계 근거를 저장하고
   `c2h send --from planner --to executor --story <ID> --message '스토리 경로·범위·준비 근거'`를 실행한다.
   선택한 준비 스토리가 여러 개면 후보별로 기록하되 실제 구현 승인은 executor에서 하나만 받는다.
   같은 내용의 미처리 메시지는 중복 전송하지 않는다. 내용이 바뀌면 기존 메시지와 차이를 기록한다.
   **executor pane → `/executor` → 스토리 선택**을 안내한다. 전달은 구현 승인이 아니다.
2. **스토리 검토·보강하기 (`refine`)**: 누락·완료 조건·위험을 검토하고 문서를 보강한 뒤 다시 선택 UI를 연다.
3. **이 내용 논의하기 (`discuss`, chat about this)**: 논의할 내용을 묻고 답변을 기다린다. 자동 인계·구현하지 않는다.

취소·무응답·타임아웃은 인계 승인 없음이다. 도구/UI가 없으면 확장 신뢰·설치·`/reload`를 안내하고 멈춘다.
인계 후에도 AWAITING_APPROVAL/담당 planner를 유지한다. 메시지 ID와 문서 경로를 표시하고,
저장·알림 성공을 상대 CLI의 작업 시작이라고 표현하지 않는다. planner → executor는 수동 시작이다.

## 실행 완료 선택

executor는 구현 또는 승인된 FIX와 검증을 마친 뒤 결과를 저장하고,
Claude `AskUserQuestion`의 `multiSelect: false`로 다음 세 가지를 제시한다.

1. **리뷰어에게 넘기기**: 리뷰 요청 승인이다. 스토리·범위·검증 기록을 다시 확인한 뒤
   `.claude/skills/harness-review/SKILL.md`를 읽어 같은 세션에서 인계·백그라운드 대기를 실행한다.
   사용자에게 명령 재입력을 요구하지 않는다. 리뷰 결과 수정 승인과는 별개다.
2. **보강하기**: 무엇을 보강할지 묻고 합의한 기존 승인 범위만 보강·검증한 뒤 다시 선택한다.
   범위 확대·의존성 추가·이전 리뷰의 미선택 수정안은 별도 승인을 받는다.
3. **이 내용 논의하기 (chat about this)**: 질문·설계·구현 의도를 논의한다. 소스 수정·인계하지 않는다.

취소·빈 응답·타임아웃·자동 계속은 승인 아님. UI가 없으면 멈춘다. 보강·논의 선택만으로 리뷰 요청하지 않는다.
직접 `/harness-review` 입력도 지원한다. 수신자가 바빠도 tmux 키 입력을 주입하지 않는다.

## 인계와 자동 수신

1. planner는 스토리 범위·완료 조건·남은 결정을 기록하고 AWAITING_APPROVAL에 둔다.
   index.md에는 기능명·문서 링크·상태·착수 가능 여부가 있는 완료 체크리스트를 표시한다.
   DONE만 체크하며 구현 완료·리뷰 대기·FIX는 미완료 상태다. 스토리 문서가 정본이며 index는 요약이다.
   구현 준비가 끝나면 다음 담당 executor에게 인계할 근거를 스토리에 남긴다.
2. `/executor`는 준비된 스토리를 AskUserQuestion의 단일 선택 UI로 보여준다. 호출만으로 승인하지 않는다.
   사용자 선택을 구현 승인·인계 수락 근거로 기록하고 IMPLEMENTING/담당 executor 및 CURRENT.md를 갱신한다.
   inbox의 planner 메시지를 실제 문서와 대조하고 수락 기록 후 해당 메시지만 ack한다.
   진행 중인 스토리가 있으면 다른 스토리를 시작하지 않는다. 구현·검증 후 실행 완료 선택을 제시한다.
3. `/harness-review`로 executor가 REVIEW/담당 reviewer와 결과를 기록한 뒤 `c2h review <ID>`를 실행한다.
   CLI는 Git HEAD·index·추적 파일·무시되지 않은 미추적 파일의 기준 지문과 요청 ID를 저장한다.
   `.harness/` 협업 기록과 Git ignored 파일은 기준에서 제외한다. submodule은 자동 검토 대상에서 지원하지 않는다.
   구현 기준과 미검증 항목은 implementation.md에 사람이 읽을 수 있게 별도로 기록한다.
4. Pi 확장은 reviewer가 유휴이고 대기 입력·작성 중 입력이 없을 때 요청을 한 번 전달한다.
   새 세션에 모델 호출을 만들지 않고 이미 열린 reviewer 세션에서 시작한다.
   실제 역할·승인·현재 스토리·기준 확인과 리뷰는 에이전트가 수행한다. 수신 자체가 검증 통과는 아니다.
5. reviewer는 diff·변경 파일과 위험 확인에 필요한 직접 호출부·타입·테스트 코드만 읽는다.
   전체 저장소 탐색·브라우저·서버·빌드·테스트·QA 실행은 하지 않는다. 검증 책임은 executor에게 있다.
   review-N.md에 계획 충족·코드 결함·잠재 위험, 요청 ID·기준·검토 범위·R1/R2 등의 지적 ID·
   심각도·파일:라인·실패 조건·수정안을 기록한다. 실행자 증거 인용과 직접 검증을 구분한다.
6. 결과 저장 후 REVIEW_DECISION/담당 executor와 CURRENT.md를 맞춘다.
   `c2h reply REQUEST_ID --review 결과경로`로 회신한다. 지적이 없어도 회신한다.
   새 qa-N.md는 요구하지 않는다. 기존 `--qa` 회신은 호환용으로 읽고 파일 무결성도 확인한다.
   typed review_request는 먼저 ack하지 않는다. reply가 회신 저장 후 요청을 보관한다.
7. executor는 Bash의 `run_in_background: true`로 `c2h wait REQUEST_ID --timeout 1800`을 실행한다.
   Claude의 백그라운드 완료 알림으로 결과를 읽고 아래 브리핑만 수행한다. 반복 LLM 폴링은 하지 않는다.

## 리뷰 브리핑과 결정

executor는 결과를 그대로 수용하지 않고 실제 코드와 대조한다. 아래 내용을 한 번에 섹션별로 브리핑하고
`.harness/stories/<ID>/review-brief.md`에 최신 요청 ID·기준과 함께 기록한다.

| 항목 | 내용 |
| --- | --- |
| 지적 | 지적 ID·reviewer의 근거·심각도 |
| 확인 | executor가 실제 코드에서 확인한 결과 |
| 권고 | 수정 필요 / 추가 확인 / 반영 불필요와 이유 |
| 수정안 | 변경 범위·영향·예정 검증 |

- 브리핑 전에는 소스를 수정하지 않는다. 섹션마다 반복 질문하지 말고 사용자 선택을 기다린다.
- `/accept`는 AskUserQuestion의 다중 선택 UI를 연다. 선택한 수정안만 승인하며 나머지는 보류한다.
- `/feedback`은 단일 선택 UI에서 항목을 고른 뒤 의견을 받는다. 바뀐 수정안은 새 승인 전까지 실행하지 않는다.
- 사용자에게 내부 스토리/지적 ID 입력을 요구하지 않는다. 구별 가능한 제목·범위로 표시하고 내부 ID와 정확히 대응시킨다.
- 취소·빈 응답·타임아웃·자동 계속은 승인 없음이다. 기본값으로 전체 수락하거나 UI 부재를 텍스트 ID 입력으로 우회하지 않는다.
- 긴 목록은 도구 옵션 한도에 맞춰 나눈다. 페이지 이동은 승인이 아니며, 여러 페이지에서 수정안을 고르면 마지막 요약에서 적용 여부를 확인한다.
- 선택 후에는 현재 작업·문서·리뷰 기준을 다시 검증한다. 그동안 바뀐 수정안이나 범위에 이전 선택을 적용하지 않는다.
- 승인한 수정은 FIX → 구현·검증 → 실행 완료 선택의 리뷰 인계 또는 `/harness-review` 순서로 다시 검토한다.
  일부 항목을 수정한 뒤에는 이전 기준의 나머지 항목을 자동 적용하지 않는다. 새 리뷰 기준에서 확인한다.
- 수정이 없으면 불필요한 변경을 만들지 않는다. 필요한 수동 테스트·학습·완료 게이트는 유지한다.
- 코드리뷰/Fix·실행자 QA/Fix 각각 최대 3회. 같은 실패 2회 반복이면 BLOCKED. 임의 모델 변경·자동 DONE 금지.
- 필요한 수동 테스트 안내·사용자 결과 기록은 executor가 맡는다. 테스트 증거·사용자 확인·리뷰 결정이 정리된 후에만
  LEARNING/담당 planner로 기록하고 결과 경로를 send한다. planner pane에서 `/harness-resume`으로 수동 재개한다.
- 브리핑을 저장하고 인계 수락을 기록한 뒤 executor 결과 메시지를 ack한다. 보관된 메시지로도 wait 검증은 가능하다.
- 각 담당자는 상태 변경 후 index.md 체크리스트도 갱신한다. 마지막 완료 게이트를 통과하기 전에는 체크하지 않는다.

## 중단·복구

- 소스 지문이 달라지거나 요청·스토리·회신이 불일치하면 결과를 적용하지 않는다. 원인을 확인하고 재리뷰한다.
- pending 요청이 있으면 중복 리뷰를 보내지 않는다. 취소가 필요하면 사용자 확인과 스토리 기록 후
  `c2h ack reviewer REQUEST_ID`로 보관한다. 기존 대기 작업도 Claude `/tasks`에서 중단한다.
- reviewer 중단 후에는 해당 세션에서 `/reviewer`로 미처리 요청을 재시도한다. reply 재실행은 회신을 중복 생성하지 않는다.
  확장이 없으면 `/harness-reviewer` 후 `inbox 확인하고 리뷰 진행`으로 수동 처리하고 같은 요청 ID에 reply한다.
  새 CLI를 띄우거나 요청을 중복 전송하지 않는다. busy·대기 입력·작성 중 입력이 있으면 자동 수신은 대기한다.
- wait는 30분 후 종료한다. 타임아웃은 리뷰 실패나 승인으로 취급하지 않는다.
  Claude 세션 종료·백그라운드 작업 취소·권한 거부 시 자동 브리핑이 끊길 수 있다.
  사용자 확인 후 같은 요청 ID로 wait를 다시 시작한다. 명령 실패를 숨기거나 새 에이전트를 실행하지 않는다.
- 기존 프로젝트는 이 문서뿐 아니라 WORKFLOW.md·역할 규칙·RESUME.md의 관련 부분도 병합한다.
  기존 파일을 덮어쓰지 않는 init의 보존 정책은 유지된다.

## 보장 범위

CLI는 요청 상관관계·파일 경로·소스 변경·중복 요청/회신·대기 기한을 검사한다.
모델의 실제 승인 해석·코드 품질·브리핑 충실도까지 프로그램이 보장하지는 않는다.
역할과 문서 계약은 OS 보안 경계가 아니다. 기존 테스트 통과를 실제 세 CLI의 모델 동작 검증으로 표현하지 않는다.
