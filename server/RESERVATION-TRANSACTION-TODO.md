# 예약 트랜잭션 실습 TODO

목표는 정답 코드를 재현하는 것이 아니라 **예약 한 건이 두 테이블에 나뉘어 있을 때 무엇이 깨질 수 있는지 스스로 찾고, 어떤 DB 장치로 막는지 직접 설계하는 것**입니다. 이 문서는 구현 방법을 알려주지 않습니다. 지켜야 할 규칙(불변식)과 그것이 깨지는 상황, 생각할 질문만 줍니다.

경로는 `server/` 기준입니다. 개발·운영 데이터로 실습하지 않습니다.

### 바깥에서 고정한 모양

함수 이름·나누는 방식은 자유입니다. 다만 **이미 누군가 부르고 있는 것**은 그 모양을 따라야 합니다.

- **컨트롤러 → 서비스:** `reservations.controller.ts`를 읽고, 서비스가 어떤 메서드를 갖고 어떤 결과(`kind`)를 돌려줘야 컨트롤러가 404·409·422를 만들 수 있는지 거꾸로 추론합니다.
- **e2e 테스트 → 저장소:** 롤백 테스트가 `app.get(ReservationsRepository)`로 저장소를 꺼내 `transaction(...)`과 `replace(...)`를 직접 부릅니다. 테스트 코드에서 두 메서드의 인자 모양을 읽어 그대로 맞춥니다.
- 그 외 저장소 메서드는 **서비스를 쓰다가 필요해질 때** 만듭니다. 저장소를 먼저 설계하지 않습니다.

> 지금 `pnpm --dir server build`가 실패하는 것이 정상입니다. 오류 목록이 첫 요구사항입니다.

## 3. 무엇이 불변식을 깨는가 — 개념

### 문제 A — 일부만 저장된다 (I1·I2)

예약 한 건을 저장하려면 SQL이 여러 번 필요합니다. 두 번째 SQL이 실패하면 첫 번째 결과는 어떻게 되나요? 그 상태에서 I1·I2는 성립하나요?

필요한 규칙은 **전부 반영되거나, 전부 반영되지 않거나**입니다. 이것이 쓰기 트랜잭션이 존재하는 이유입니다.

### `tx`는 무엇이고 왜 함수 사이로 넘기나

Drizzle의 `db.transaction(callback)`에서 콜백이 받는 `tx`는 **이미 시작된 트랜잭션 안에서 쿼리하는 통로**입니다. 콜백이 정상 종료하면 커밋, 예외를 던지면 롤백합니다.

```text
서비스: "예약 수정"이라는 작업 단위를 정한다
  └─ 트랜잭션 시작 → tx
       ├─ (tx로) 읽기·확인
       ├─ (tx로) 쓰기 1
       └─ (tx로) 쓰기 2 …
     콜백 정상 종료 → COMMIT / 예외 → ROLLBACK
```

생각할 것:

- 작업을 여러 함수로 나눴을 때, 그중 하나가 `tx` 대신 루트 `db`로 쿼리하면 무슨 일이 생기나? (같은 연결인가? 함께 롤백되나?)
- 함수마다 각자 `db.transaction`을 열면 하나의 작업으로 묶이나?
- 서비스는 DB를 직접 갖지 않는데, 작업 범위를 어떻게 정하게 할 것인가?
- 서비스가 거부 결과(`{ kind: 'rejected' }`)를 **반환**하는 것은 롤백 신호인가? 그렇다면 거부 판단은 쓰기 전과 후 중 언제 해야 하나?
- 저장 중 난 예외를 잡아서 성공 결과로 바꾸면 어떻게 되나?

### 문제 B — 입력을 믿으면 깨진다 (I3·I4)

클라이언트는 `customerId`, `treatmentIds`, `startAt`만 보냅니다. 그런데 저장할 행에는 이름·전화·시술명·소요시간·종료 시각이 필요합니다.

- 저장할 값은 어디서 와야 하나? 그 값을 언제 확정해야 하나 — 쓰기 전인가, 쓰는 도중인가?
- 존재하지 않는 고객·시술 id가 오면? 소요시간 합이 너무 커서 종료 시각을 계산할 수 없으면? (계약의 `ReservationRejection` 사유 3가지를 보세요)
- **수정**에서, 기존에 있던 시술의 이름·소요시간을 지금 마스터에서 다시 읽어 오면 I3은 어떻게 되나? 그럼 기존 값은 어디서 가져와야 하나?
- 고객·시술 확인 조회도 트랜잭션 안(`tx`)에서 해야 하나? 밖에서 해도 되나? 각각의 장단점은?

예약 전용 계산(소요시간 합, 종료 시각, 스냅샷 구성)은 주어지지 않습니다. 직접 정합니다. 한국 시간 날짜 계산은 범용 유틸 `@o2o/shared/date`(`shared/date/kst.ts`)를 씁니다. 예: `dayRange`(그날 0시~다음 날 0시), `addMinutes`(시각 + 분, 달력 범위를 넘으면 `null`).

### 문제 C — 동시에 들어오면 깨진다 (I5)

두 요청이 같은 예약을 동시에 취소(또는 수정과 취소)합니다. 각 요청에 트랜잭션이 있어도 둘 다 "아직 취소 안 됨"을 읽고 진행할 수 있습니다. **트랜잭션은 원자성을 주지, 동시 요청을 줄 세워 주지는 않습니다.**

- 두 요청이 같은 행을 놓고 차례를 지키게 하려면 무엇이 필요한가? (`SELECT … FOR UPDATE`를 찾아보세요)
- 그 잠금은 언제 얻고 언제 풀리나? 잠그기 **전에** 읽은 "취소 여부"는 믿을 수 있나?
- 수정 경로와 취소 경로가 서로 다른 순서로 행을 다루면?
- 잠금과 별개로, 갱신 SQL 자체에 "취소되지 않은 행만" 조건을 거는 것은 왜 의미가 있나? 둘은 각각 무엇을 막나?
- 이 잠금이 **막지 못하는** 것은 무엇인가? (다른 예약과의 시간 겹침, 오래된 수정 화면의 덮어쓰기)

### 문제 D — 읽기만 해도 섞인다 (I6)

목록은 본문과 시술을 두 번의 쿼리로 읽습니다. 그 사이에 다른 요청이 수정을 커밋하면?

- PostgreSQL 기본 `READ COMMITTED`에서 같은 트랜잭션 안의 두 쿼리는 같은 시점을 보나?
- `REPEATABLE READ`는 무엇을 보장하나? `READ ONLY`는?
- 쓰기의 원자성(문제 A)을 지켰는데도 읽는 쪽에 문제가 남는 이유는?

‘시술 스냅샷’(예약 당시 값을 복사해 저장한 데이터)과 ‘DB 스냅샷’(쿼리가 바라보는 시점)은 다른 뜻입니다.

## 4. 실습 순서

각 실습은 같은 순서로 진행합니다.

1. **깨지는 상황 적기:** 아무 장치 없이 구현하면 어떤 불변식이 어떤 순서의 사건에서 깨지는지 말로 적는다.
2. **서비스:** 작업 단위(트랜잭션 범위)와 판단 순서를 적는다. 어디서 거부하고, 어디서 쓰는가? 저장소 메서드는 이름·시그니처만 정하고 본문은 `throw`로 둔다.
3. **저장소:** 서비스가 요구한 모양대로 SQL을 채운다. 모든 쿼리가 받은 `tx`를 쓰는지 확인한다.
4. **확인:** 해당 테스트만 `-t`로 실행한다. 실패하면 1에 적은 설명과 비교한다.

### 실습 2 — 예약 하나를 등록하고 다시 읽기 (I1·I2·I4)

- **깨지는 상황:** 본문은 들어갔는데 시술 행 저장이 실패한다. / 없는 시술 id를 받았는데 본문을 먼저 써 버렸다.

  - 시술 "순서"(요청에 담긴 순서)를 어떻게 남길 것인가?

- **확인:**
  - 「30분+60분을 23:30에 등록하면 총 90분, 다음 날 01:00 종료가 응답·DB·재조회에서 같다」
  - 「없는 고객·시술, 계산할 수 없는 종료 일시는 사유와 함께 422로 거부한다」
  - 「한국 시간 그날 0시 이상 다음 날 0시 미만에 시작한 예약을 시작 시각·id 순으로 준다」

### 실습 3 — 예약 수정과 롤백 (I1·I2·I3)

- **깨지는 상황:** 본문 시간은 바뀌었는데 시술 행 교체가 중간에 실패한다. / 시간만 바꿨는데 기존 시술 소요시간이 지금 마스터 값으로 바뀐다.
- **생각:**
  - 시술 목록을 바꾸는 방법은? 변경분만 계산할 수도, 해당 예약의 시술 행을 지우고 다시 넣을 수도 있다. 어느 쪽이 단순하고, 어느 쪽이든 트랜잭션이 필요한 이유는?
  - 지우는 것은 `reservation_treatments`의 **그 예약 행**뿐이다. `treatments` 마스터나 다른 예약의 행이 아니다.
  - 수정의 확인·계산에는 기존 예약의 무엇이 필요한가? 그것을 언제, 어떤 방식으로 읽어야 하나? (문제 C와 연결)
  - 없는 예약, 이미 취소된 예약은 어떤 결과로 끝나야 하나? 쓰기 전에 판단하나?
- [ ] 수정을 하나의 작업으로 구현한다.
- [ ] 롤백 테스트가 부르는 저장소 메서드를 구현한다. 모든 쓰기가 같은 `tx`를 쓴다.
- **확인:**
  - 「시술 마스터를 바꿔도 저장한 예약은 그대로고, 시간만 바꾸면 기존 스냅샷을 쓴다」
  - 「시술을 추가하면 기존 것은 예약 당시 값, 추가분만 지금 값으로 합산한다」
  - 「트랜잭션이 실패하면 예약 본문·시술 스냅샷을 일부만 바꾸지 않는다」

롤백 테스트는 교체가 끝난 뒤 일부러 예외를 던집니다. 함께 롤백되는지는 확인하지만, 각 SQL 실패 지점까지 따로 주입하지는 않습니다.

### 실습 4 — 최초 취소 보존과 동시 요청 (I5)

- **깨지는 상황:** 두 취소 요청이 모두 "미취소"를 읽고 각자 시각·사유를 쓴다. / 수정이 "미취소"를 읽은 직후 취소가 커밋되고, 수정이 취소를 덮어쓴다.
- **생각:** 문제 C의 질문들. 그리고 이미 취소된 예약을 만났을 때 두 번째 요청은 무엇을 돌려받아야 하나? (계약의 409 응답 데이터)
- [ ] 취소를 구현한다. 본문·시술은 지우지 않고 취소 시각·사유만 남긴다.
- [ ] 수정·취소 두 경로가 같은 규칙으로 행을 다루는지 코드로 따라간다.
- **확인:**
  - 「원본·복수 시술을 남기고 기본 목록에서만 빼며, 취소 포함에서 최초 취소 시각·사유를 본다」
  - 「동시에 두 번 취소해도 하나만 기록되고 다른 하나는 최초 기록을 받는다」
  - 「수정과 취소가 겹쳐도 취소된 예약을 되살리지 않는다」

동시성 테스트의 한 번 통과가 모든 실행 순서를 검증하지는 않습니다. 가능한 순서를 직접 그려 보고 코드로도 확인하세요.

### 실습 5 — 조회 시점 일관성 (I6)

- **깨지는 상황:** 본문은 수정 전, 시술은 수정 후 값으로 섞여 나온다.
