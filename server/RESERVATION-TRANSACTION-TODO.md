# 예약 트랜잭션 실습 TODO

목표는 메서드 채우기가 아니라 **예약 한 건을 여러 SQL로 다룰 때 무엇이 깨지는지 이해하고 막는 것**입니다. 정답 코드는 넣지 않습니다. 기존 `test/reservations.e2e-spec.ts`를 검증 기준으로 쓰므로 새 테스트를 작성할 필요는 없습니다.

이 문서의 경로는 `server/` 기준입니다. 예약 기능은 학습용 TODO 상태이며, 개발·운영 데이터로 실습하지 않습니다.

## 1. 먼저 스키마와 수정 흐름 연결하기

읽을 파일: `db/schemas/reservations.schema.ts`, `db/schemas/treatments.schema.ts`.

| 테이블 | 무엇을 담는가 | 예약 한 건과의 관계 |
| --- | --- | --- |
| `treatments` | 현재 판매하는 시술의 이름·소요시간 등 | 예약에 선택할 원본 목록, 즉 시술 마스터 |
| `reservations` | 예약 고객 정보, 시작·종료 시각, 취소 정보 | 예약 본문 한 행 |
| `reservation_treatments` | 해당 예약에 선택한 시술의 당시 이름·소요시간·순서 | `reservationId`로 본문에 연결되는 여러 행 |

여기서 **스냅샷**은 예약 당시 값을 복사해 남긴 기록입니다. 시술 마스터에서 소요시간을 바꾸더라도 기존 예약의 종료 시각까지 따라 바뀌면 안 되므로, 예약에는 별도의 값을 저장합니다.

예를 들어 10:00 예약에 30분 시술 하나가 있으면 다음 두 곳에 정보가 나뉩니다.

- `reservations`: 시작 10:00, 종료 10:30.
- `reservation_treatments`: 해당 예약 ID, 시술 이름, 소요시간 30분.

여기에 60분 시술을 추가하면 본문의 종료 시각은 11:30, 예약 시술 목록은 30분+60분이 되어야 합니다. **서로 다른 테이블의 값이 함께 맞아야 한 번의 예약 수정이 완성**됩니다.

### 왜 ‘본문 변경 → 기존 시술 삭제 → 새 시술 저장’인가?

기존 구현은 예약 수정 시 시술별 변경분을 계산하지 않고, **해당 예약의 시술 스냅샷 행을 모두 지운 뒤 수정된 목록으로 다시 저장**하는 방식을 택했습니다. 시간만 바뀌는 요청도 같은 교체 흐름을 사용했습니다.

이때 삭제하는 것은 `reservation_treatments`의 해당 예약 행입니다. **`treatments`의 시술 상품이나 다른 예약의 시술을 삭제하는 것이 아닙니다.** 유지하는 시술의 스냅샷 값은 서비스의 `draft`에서 가져옵니다.

전체 교체는 이 프로젝트의 구현 선택이지, 예약 수정이라면 반드시 삭제·삽입해야 한다는 뜻은 아닙니다. 이번 실습은 기존 교체 방식을 유지합니다.

- [ ] 스키마를 보며 예약 ID 하나에 본문과 시술 행들이 어떻게 연결되는지 설명한다.
- [ ] 시술 마스터 수정과 예약 시술 스냅샷 교체가 어떻게 다른지 설명한다.

## 2. 트랜잭션·tx·잠금은 무엇을 해결하는가?

### 문제 A — 일부만 저장되는 실패

본문 수정과 기존 스냅샷 삭제는 성공했는데 새 스냅샷 저장이 실패하면, 예약에 시술이 없는 상태가 남을 수 있습니다. 필요한 규칙은 **모두 성공하면 반영, 중간에 실패하면 모두 원래대로**입니다. 이것이 쓰기 트랜잭션을 묶는 동기입니다.

### tx를 왜 함수 사이에 전달하나?

`db.transaction`의 콜백이 받는 `tx`는 **이미 시작된 트랜잭션 안에서 쿼리하는 통로**입니다. SQL 문자열이나 저장할 데이터가 아닙니다. 이 Drizzle API에서는 콜백이 정상 완료되면 커밋하고, 예외로 실패하면 롤백합니다. 직접 `BEGIN`·`COMMIT`을 적는 실습은 아닙니다.

서비스가 시작한 한 작업이 `insert`, `replace`, `markCancelled` 같은 여러 함수로 나뉘어 있어도, 같은 `tx`로 쿼리하면 같은 DB 연결의 같은 트랜잭션에 참여합니다. **트랜잭션 객체를 꺼내 수정하는 것이 아니라, 그 안에서 작업할 권한을 함수에 넘기는 것**으로 이해하면 됩니다.

```text
서비스: 예약 수정이라는 작업 단위를 정한다
  └─ repository.transaction(work): DB 트랜잭션을 연다
       └─ work(tx)
            ├─ lock(tx, ...)
            ├─ 고객·시술 확인과 draft 계산
            └─ replace(tx, ...)
                 ├─ 본문 변경
                 ├─ 해당 예약의 기존 스냅샷 삭제
                 └─ insertTreatments(tx, ...)
```

콜백 안이라는 이유만으로 모든 쿼리가 자동 참여하지는 않습니다. 중간 함수가 `tx` 대신 루트 `this.db`로 쿼리하면 그 작업은 별도 연결에서 실행되어 함께 롤백되지 않을 수 있습니다. 함수마다 새 트랜잭션을 따로 열어도 하나의 작업으로 묶이지 않습니다.

기존 `transaction(work)` 메서드는 DB를 직접 갖지 않는 서비스가 작업 범위를 정하도록 연결하는 역할입니다. 이 래퍼 자체가 필수 문법인 것은 아닙니다. `findCustomer`·`findTreatments`에 남아 있는 `tx` 사용을 읽고 호출 경로를 따라가 보세요.

또한 `{ kind: 'rejected' }` 반환은 예외가 아니므로 자동 롤백 신호가 아닙니다. 현재 흐름은 거부 여부를 **쓰기 전에** 판단해야 합니다. 저장 중 예외를 성공 결과로 바꿔 삼키면 부분 변경이 커밋될 수 있습니다.

### 문제 B — 동시에 취소하거나 수정하는 요청

각 요청에 트랜잭션이 있어도, 둘 다 ‘아직 취소되지 않음’을 읽고 시작할 수 있습니다. **트랜잭션으로 묶었다고 모든 동시 요청이 자동으로 순서대로 실행되지는 않습니다.**

`lock`의 행 잠금은 같은 예약을 다루는 수정·취소 요청을 차례로 처리하려는 장치입니다. 잠금은 트랜잭션 종료까지 유지됩니다. 현재 수정·취소 경로가 모두 같은 본문 행을 먼저 잠그는 규칙을 지켜야 합니다.

`markCancelled`의 ‘취소되지 않은 행만 변경’ 조건은 최초 취소 기록을 덮어쓰지 않기 위한 방어입니다. 행 잠금과 조건부 갱신은 역할이 다릅니다. 이 잠금이 다른 예약의 시간 겹침이나 오래된 수정 화면의 덮어쓰기까지 막아주지는 않습니다.

### 문제 C — 읽기만 해도 서로 다른 시점이 섞임

목록은 본문과 시술 스냅샷을 두 번의 조회로 읽습니다. 본문을 읽은 뒤 다른 요청이 수정을 커밋하면, 이전 종료 시각과 새로운 시술 목록이 섞일 수 있습니다. 작성자가 원자적으로 저장해도 읽는 쪽에는 별도 문제가 남습니다.

PostgreSQL 기본 `READ COMMITTED`에서는 트랜잭션 안에서도 각 조회가 다른 시점을 볼 수 있습니다. 이번 실습의 `REPEATABLE READ`는 두 조회가 같은 DB 스냅샷을 보게 합니다. `READ ONLY`는 쓰기를 금지하는 설정이지, 이것만으로 일관된 시점을 보장하지는 않습니다.

‘예약 당시 값을 복사한 시술 스냅샷’과 ‘조회 트랜잭션의 DB 스냅샷’은 다른 뜻입니다. 전자는 저장한 데이터, 후자는 조회가 바라보는 시점입니다.

## 3. 문제를 따라가는 실습 순서

모든 확인 테스트는 `test/reservations.e2e-spec.ts`에 있습니다. 아래 인용은 기존 테스트 이름입니다. 테스트 하나도 등록·조회 등 여러 함수를 거치므로, TODO 하나를 채웠다고 즉시 통과하지 않을 수 있습니다.

### 실습 1 — 트랜잭션 통로 연결

- **문제:** 함수별로 실행한 SQL을 어떻게 하나의 성공·실패 단위에 넣을까?
- **질문:** `work`가 받는 값과 돌려주는 값은 무엇인가? 작업의 예외는 호출자까지 전달되는가?
- [x] 저장소 `transaction`에서 작업 함수에 `tx`를 전달하고 비동기 결과·예외를 전달한다.
- **확인:** 아래 롤백 테스트의 호출 구조부터 읽는다. 실행 검증은 등록·조회·교체 구현 후 한다.
  - 「트랜잭션이 실패하면 예약 본문·시술 스냅샷을 일부만 바꾸지 않는다」

### 실습 2 — 예약 하나를 끝까지 등록하고 다시 읽기

- **문제:** 본문만 저장되고 시술 행 저장이 실패하면 어떻게 되는가? 등록한 값을 다시 읽으려면 어느 테이블들이 필요한가?
- **질문:** 새 예약 ID는 어디서 얻는가? 시술 순서를 어떻게 남기는가? 클라이언트가 아니라 서버가 종료 시각을 계산하는 이유는 무엇인가?
- [ ] 저장소 `insert`·`insertTreatments`에서 본문과 스냅샷을 같은 `tx`로 저장한다.
- [ ] 서비스 `createReservation`에서 기존 `draft`를 사용해 검증 후 저장을 묶는다.
- [ ] 저장소 `findStartingBetween`에서 본문과 시술을 조합해 날짜별 목록을 반환한다. 같은 조회 시점을 지키는 것은 실습 5에서도 확인한다.
- **확인:**
  - 「30분+60분을 23:30에 등록하면 총 90분, 다음 날 01:00 종료가 응답·DB·재조회에서 같다」
  - 「없는 고객·시술, 계산할 수 없는 종료 일시는 사유와 함께 422로 거부한다」
  - 「한국 시간 그날 0시 이상 다음 날 0시 미만에 시작한 예약을 시작 시각·id 순으로 준다」

### 실습 3 — 예약 교체와 롤백

- **문제:** 본문 변경·기존 스냅샷 삭제·새 스냅샷 저장 중간에 실패해도, 변경 전 예약이 온전히 남아야 한다.
- **질문:** 세 쿼리 중 하나라도 다른 연결로 실행되면 롤백 결과가 어떻게 달라질까? 기존 시술은 왜 현재 마스터 값으로 다시 채우면 안 될까?
- [ ] 저장소 `lock`에서 해당 예약 행을 `FOR UPDATE`로 읽고 시술도 조합한다.
- [ ] 저장소 `replace`에서 취소되지 않은 본문과 해당 예약의 스냅샷만 교체한다. 모든 쓰기에 같은 `tx`를 쓴다.
- [ ] 서비스 `updateReservation`에서 잠금 → 없음/취소 여부 확인 → `draft` → 교체를 하나의 트랜잭션으로 묶는다.
- **확인:**
  - 「시술 마스터를 바꿔도 저장한 예약은 그대로고, 시간만 바꾸면 기존 스냅샷을 쓴다」
  - 「시술을 추가하면 기존 것은 예약 당시 값, 추가분만 지금 값으로 합산한다」
  - 「트랜잭션이 실패하면 예약 본문·시술 스냅샷을 일부만 바꾸지 않는다」

롤백 테스트는 `replace`가 끝난 뒤 일부러 예외를 던집니다. 함께 롤백되는지는 확인하지만, 각 INSERT 실패 지점까지 따로 주입하는 테스트는 아닙니다.

### 실습 4 — 최초 취소 보존과 동시 요청

- **문제:** 두 요청이 동시에 취소하면 어떤 시각·사유를 남길까? 수정 요청이 취소 요청과 겹치면 어떻게 할까?
- **질문:** 잠금을 언제 얻고 언제 놓는가? 취소 여부를 잠그기 전에만 읽으면 안전할까? 이미 취소된 행을 갱신하지 못했을 때 어떤 결과를 전달해야 할까?
- [ ] 저장소 `markCancelled`에서 미취소 행에만 시각·사유를 기록하고 본문·시술 기록은 유지한다.
- [ ] 서비스 `cancelReservation`에서 같은 트랜잭션의 잠금과 상태 확인을 거쳐 최초 취소만 허용한다.
- [ ] 수정·취소가 모두 같은 예약 행을 잠근 뒤 상태를 판단하는지 따라가 본다.
- **확인:**
  - 「원본·복수 시술을 남기고 기본 목록에서만 빼며, 취소 포함에서 최초 취소 시각·사유를 본다」
  - 「동시에 두 번 취소해도 하나만 기록되고 다른 하나는 최초 기록을 받는다」
  - 「수정과 취소가 겹쳐도 취소된 예약을 되살리지 않는다」

동시 요청 테스트의 한 번 통과만으로 모든 실행 순서가 검증되지는 않습니다. 잠금과 조건부 갱신이 어떤 순서에서도 규칙을 지키는지 코드로도 확인하세요.

### 실습 5 — 조회 도중 수정이 끝나도 한 시점 유지

- **문제:** 본문은 수정 전 값인데 시술은 수정 후 값을 읽을 수 있다.
- **질문:** 같은 `tx`로 두 번 조회하는 것만으로 충분한가? 쓰기 작업의 롤백과 읽기 작업의 격리 수준은 무엇이 다른가?
- [ ] `findStartingBetween`의 두 조회가 같은 `tx`의 `REPEATABLE READ`·`READ ONLY` 트랜잭션에 참여하는지 확인한다.
- **확인:**
  - 「목록을 읽는 도중 수정이 끝나도 한 예약의 본문·시술을 서로 다른 시점으로 섞지 않는다」

이 테스트는 테이블 잠금으로 조회를 도중에 멈춰 상황을 만듭니다. 제품 코드에 똑같은 테이블 잠금을 추가하라는 뜻은 아닙니다.

## 4. 실행과 완료 기준

테스트 전용 PostgreSQL DB와 `TEST_DATABASE_URL`을 준비한 뒤 저장소 루트에서 실행합니다. 개발 DB로 대체하지 마세요. 환경 설정 실패는 TODO 때문에 실패하는 테스트와 구분합니다.

```bash
# 기존 테스트 전체
pnpm --dir server test:e2e

# 예: 등록 경로 한 사례부터 확인

# 타입·빌드 오류도 확인
```

실행 흐름은 **실패 확인 → 필요한 최소 구현 → 같은 테스트 재실행 → 통과 후 정리**입니다. 기반 함수가 비어 있으면 여러 테스트가 한꺼번에 실패하는 것이 정상입니다. 테스트를 삭제하거나 기대 결과를 바꿔서 통과시키지 않습니다.

- [ ] 기존 e2e 전체와 서버 빌드가 통과한다.
- [ ] `tx` 대신 루트 `db`를 썼을 때 어떤 보장이 사라지는지 설명할 수 있다.
- [ ] 롤백·행 잠금·조회 격리 수준의 차이를 각각 예약 사례로 설명할 수 있다.
- [ ] 고객·시술 조회와 `draft`, 기존 스냅샷 유지, 날짜 필터, 오류 응답 동작을 보존한다.

미리 남겨둔 도우미·계약·테스트는 재사용합니다. 관련 없는 리팩터링, 예약 시간 겹침 방지, 새 테스트 작성은 이번 실습 범위가 아닙니다.
