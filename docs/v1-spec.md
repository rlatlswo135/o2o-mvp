# o2o V1 — 사장님용 네일샵 운영 관리: 도메인·개발 기준서

기존 `.harness/`의 `v1-scope.md`·`index.md`·`design/README.md`·`ui-structure.md`와 현재 코드를 바탕으로 2026-10-19에 한 문서로 추출했다. 하네스를 걷어내고 스토리·디자인을 다시 짤 때의 입력이다.
기능 범위 합의 문서이며 개별 스토리 승인·구현·검증 완료를 뜻하지 않는다. **확정**과 **미정**을 구분해 적었다.

---

## 1. 사용자와 운영

- 첫 도입 대상은 사용자 아내의 네일샵이다. 현재 사장님 포함 시술자 2명이며 인원 변경을 지원한다.
- 사장님과 직원이 하나의 기기에서 사장님 로그인 세션을 공유한다. 직원별 로그인·권한 시스템은 제외한다.
- 로그인 계정과 예약 담당자는 다른 개념이다. 사장님도 예약 담당자가 될 수 있다.
- 향후 다른 서비스 업종 확장이 목표지만, 초기에 다업종 기능이나 범용 엔진은 만들지 않는다.
- 실고객 데이터는 인증·접근 보호와 운영 준비가 끝난 뒤에만 사용한다.

## 3. 확정 업무 규칙

### 3.1 예약과 일정

- 담당자별 독립 일정 화면은 필수가 아니다. 담당자별 예약·가용시간 **데이터**는 필수다.
- 사장님이 담당자의 반복되는 기본 근무시간과 날짜별 변경(출퇴근 시간·휴무)을 관리한다. 직원 로그인·직원 직접 스케줄 입력은 추가하지 않는다.
- 날짜별 변경이 있으면 해당 날짜에 우선 적용한다. 예약 가능 구간은 해당 날짜의 근무시간에서 예약·차단 구간을 제외해 판단한다.
- 예약 생성·변경 과정에서 대상 담당자의 예약·차단 시간과 가용 여부를 확인할 수 있어야 한다.
- 사장님 직접 예약은 분 단위 자유 입력을 허용한다. 충돌 여부는 전체 예약 구간으로 검사한다.
- 시술 소요시간은 시술별 기본값을 쓰고, 담당자별 값이 있으면 덮어쓴다. 선택한 시술들의 시간을 합산한다.
- 시술 가격도 시술별 기본값을 쓰고, 담당자별 가격이 있으면 그 값을 우선한다.
- 소요시간 설정 변경만으로 기존 예약 시간을 바꾸지 않는다. 새 예약부터 적용한다.
- 예약 변경은 날짜·시간·담당자 변경을 포함한다. 변경 실패 시 기존 예약을 유지한다.
- 담당자 변경 시 새 담당자의 소요시간으로 종료시간을 재계산한다. 전체 구간이 다른 예약·차단과 겹치면 변경 불가다.
- 기존 활성 예약과 겹치는 시간 차단은 불가다. 먼저 예약을 명시적으로 이동·취소한 뒤 다시 차단한다. 차단을 이유로 기존 예약을 자동 취소·이동하지 않는다.
- 점심·휴무는 별도 기능이 아니라 일반 시간 차단으로 표현한다. 직원 휴무 신청·승인 기능은 제외한다.
- 취소된 예약은 삭제하지 않는다. 기본 타임테이블에서 제외하고 해당 예약이 점유한 시간을 해제한다. 다른 예약·차단·근무시간 제약은 유지한다.
- 원래 예약 내용·취소 시각·취소 사유를 보관한다. 완료 처리 시 완료 시각을 남긴다.
- 별도 상태 필드를 강제하지 않는다. 완료·취소 시각으로 예정/완료/취소를 구분하는 최소 구조를 기준으로 한다.
- 고객과 예약 이동·취소를 조율하는 일은 전화 등 서비스 밖에서 진행한다. 취소 요청의 진위 확인·분쟁 대응은 운영으로 처리하며, 취소 의사 입증 기능이나 공유 로그인 내 실제 처리자 식별 기능은 V1에 넣지 않는다.

### 3.2 회원권과 결제

- 회원권은 금액 충전형으로 고정한다. 횟수형·유형 선택 설정은 제외한다.
- 충전액이 잔액에 더해지고 사용액이 차감된다. 충전·차감·정정 이력을 추적할 수 있어야 한다.
- V1은 샵 내 **고객별 회원권 잔액 하나**로 관리한다. 추가 충전은 기존 잔액에 합산하되 충전별 실제 결제액·충전액·이력을 보관한다. 여러 회원권을 따로 보유·선택하는 기능은 수요를 확인한 뒤 검토한다.
- 실제 결제액과 충전액은 별도 금액으로 기록한다. 예: 결제 27만 원 / 충전 30만 원, 결제 30만 원 / 충전 33만 원.
- 할인·보너스 자동 계산이나 프로모션 관리 없이 사장님이 금액을 입력한다. 입력 토글·모달 등 상세 UX는 보류한다.
- 실제 결제 처리·PG·온라인 결제 연동은 제공하지 않는다. 결제는 서비스 밖에서 받고 기록만 한다.
- 잔액이 부족하면 잔액 범위에서 차감하고 나머지는 별도 결제로 기록한다. 마이너스 잔액·외상은 제외한다. 예: 시술비 5만 원 / 잔액 3만 원이면 회원권 3만 원 차감 + 별도 결제 2만 원 기록이며, 매출에는 실제 받은 2만 원만 반영한다.
- **잔액 정정**: 입력 오류는 전체 거래 취소·재등록을 강제하지 않고, 사장님이 차액과 사유를 입력해 잔액을 증감한다. 모든 잔액 변경에 증감액·변경 전후 잔액·처리 시각·사유를 기록한다(예: 과충전 정정 -1만 원, 사유 '실수로 1만 원 과충전').
- 잔액 조정은 실제 결제·환불과 별개이며 매출을 바꾸지 않는다. 사유 문구를 해석해 매출을 자동 변경하지 않는다.
- 금액 오입력 유형별 전용 정정 기능은 만들지 않는다. 사장님이 대상(회원권 잔액 또는 결제·매출 기록)을 구분해 금액을 증감하고 시각·금액·사유·변경 이력을 남긴다. 회원권 잔액 조정은 잔액만, 결제·매출 조정은 매출 집계에만 반영하며 서로 자동 연동하지 않는다.
- 자유로운 증감은 입력 권한을 뜻할 뿐 기존 검증을 없애지 않는다. 잔액 정정에도 마이너스 잔액 금지를 적용한다.
- **매출**: V1 매출은 실제 결제액 기준이다. 회원권 판매 시 실제 받은 금액은 포함하고, 회원권 잔액 사용은 추가 매출로 집계하지 않는다.
- **환불**: 해지 환불만 지원한다(일부 환불 후 계속 사용 제외). 환불액은 가게 정책에 따라 사장님이 직접 산정·입력하며 시스템에 환불 계산식을 구현하지 않는다. 환불 시 고객의 합산 잔액 전부를 소멸하고 사용 종료한다. 실제 환불액·소멸 잔액·사유·처리 시각을 기록하고 원래 결제·충전·사용 이력은 삭제하지 않는다. 매출 집계에는 소멸 잔액이 아닌 **실제 환불액만** 차감한다. 돈을 돌려주는 행위는 서비스 밖에서 처리한다.

## 4. V1 제외와 V2 합의

### 제외

- 비용 관리, 엑셀 export, 전자서명, 에이전트.
- 직원 개별 로그인, 개인 일정 공유, 화면 정보 숨김·재배치·크기 조절.
- 커뮤니티·플랫폼 회원가입·샵 홍보·이미지 기반 스타일 탐색 에이전트(추후 구상, 지금 설계하지 않음).
- 예약 생성·변경·취소 즉시 카카오 알림.

### V2 — 고객 전용 예약페이지 (합의 사항)

- 화면은 분리하되 사장님 화면과 같은 예약 데이터·충돌 규칙을 쓴다. 사장님·고객 화면은 서버의 같은 일정 데이터를 사용한다.
- 고객 회원가입 없이 이름·전화번호를 받아 사장님 측 고객 기록과 매칭한다(매칭 상세 정책 미정).
- 흐름: 시술·담당자 선택 → 문자 인증 → 최신 가능 시간 선택 → 서버 충돌 검사 후 예약 확정. 시간 임시 선점과 기기별 인증 장기 유지는 제외한다.
- 고객 시작 시간 간격은 샵별로 5/10/15/20/25/30분 중 설정한다(기준 시각 미정). 기존 시작 시간 후보를 유지하고 충돌 후보만 제외하며, 사장님 예약 종료시각을 기준으로 간격을 다시 시작하지 않는다. 시술 길이는 간격에 맞춰 반올림하지 않고 자투리 시간을 허용한다.
- 고객은 예약 생성만 가능하다. 변경·취소는 샵에 문의하고 사장님이 처리한다. 예약 전후에 변경·취소 문의 안내와 연락 수단을 제공한다.
- 샵별 예약페이지 디자인, 시술·담당자 선택, 사장님 화면 반영·신규 예약 알림의 상세 범위, 주간 스케줄 확정 방식, 몇 주 앞까지 예약을 열지는 V2에서 정한다.

## 8. 개발 방식 합의

- **역할**: client/는 AI-first 구현 + 사용자 리뷰. **server/는 사용자가 직접 구현**하며 명시 요청 없이 AI가 수정하지 않는다(필요 시 가이드·코드 리뷰만).
- **FE 구조**: `routes → features → shared` 단방향.
  - `client/src/routes/`: 페이지 조립·파일 기반 라우팅
  - `client/src/features/<feature>/`: 업무 UI·입력·상태·서버 접근
  - `client/src/shared/ui/`: 도메인 독립 공통 UI·테마 (업무 규칙 의존 금지)
  - 공통 컴포넌트는 처음부터 shared/ui에서 개발한다. 문구·상태·옵션·콜백은 소비자가 소유한다.
  - shared/ui는 `<component>/<component>.tsx` + 테스트를 함께 두고 barrel `index.ts`는 만들지 않는다.
- **상태·라우팅**: URL에 둘 날짜·필터·페이지는 TanStack Router search params, 일시적 UI·입력 상태는 기능 로컬로 둔다. nuqs는 제외한다. 개인정보는 URL에 넣지 않는다.
- **의존성**: Zustand·TanStack Table·TanStack Form은 선설치하지 않고 필요할 때 사용자가 직접 설치한다. AI는 구성·패키지·설정을 임의로 바꾸지 않는다. 패키지 매니저는 pnpm이다.
- **FE 먼저, 실연결은 나중**: 가상 데이터로 FE를 먼저 구현·리뷰하고 서버가 준비되면 실제 연결한다. FE 화면 완료와 통합 기능 완료는 구분하며, 실제 저장·조회·실패 처리 확인 없이 기능을 완료로 보지 않는다.
- **검증**: client에서 `vp check`, `vp test --run`, `vp run build`. DOM 테스트 라이브러리는 설치하지 않는 방침이라 상호작용은 브라우저로 확인한다. 실패·미실행을 PASS로 적지 않는다.
- **학습 게이트(이전 하네스의 방식, 유지 여부는 재결정)**: 스토리마다 `deep-guide.md`·`eli5.md`·`quiz.md`로 사용자 학습 확인을 받았다.
- 커밋·푸시·범위 확대·계획 밖 의존성·파괴적 작업은 별도 승인이다.

## 9. 현재 구현 현황 (2026-10-19, 코드 기준)

코드를 읽고 정리한 것이며 이번에 테스트·앱 실행은 하지 않았다.

### 스택
- 모노레포: `client/`, `server/`, `shared/`(`@o2o/shared`).
- client: React 19, TanStack Start·Router(파일 기반), TanStack Query, StyleX, flame-ui, oRPC client(OpenAPILink + ResponseValidationPlugin), Vite+(`vp`).
- server: NestJS 12 + `@orpc/nest`, drizzle-orm(1.0.0-rc.4) + PostgreSQL 17(docker `o2o-dev-db`), `pnpm db:setup`(기동·마이그레이션·시드).
- shared: zod 스키마 + oRPC 계약을 한 곳에 두고 client·server가 같이 쓴다.

### 고객(customers) — S001·S002 완료
- 계약: `list`, `get`, `create`(201, `CONFLICT`), `update`(`NOT_FOUND`·`CONFLICT`), `delete`(204, `NOT_FOUND`). 이 중 delete는 V1 스토리 목록에 없는 선구현이다.
- 입력 규칙: 이름은 trim 후 1자 이상. 전화번호는 숫자·공백·하이픈만 허용하고 구분자를 지운 8~15자리 숫자로 정규화한다. 클라이언트가 parse한 값을 서버가 다시 parse한다.
- DB: `customers(id identity PK, name, phone unique)` + 전화번호 숫자 8~15자리 check. 중복은 `onConflictDoNothing`(create)과 unique violation 변환(update)으로 처리한다.
- 서버 테스트는 Nest 기본 스캐폴딩뿐이라 customers 동작을 보호하는 테스트가 없다.
- **샵 개념이 없다.** 중복 규칙은 현재 전역 unique이며 "같은 샵의 동일 번호"는 S003(인증·샵 범위)에서 `shop_id` 도입과 함께 `(shop_id, phone)` unique로 바뀔 수 있다. 테이블이 늘기 전에 S003 결정을 먼저 하는 편이 마이그레이션 비용이 적다.
- client: `/customers` 화면(`features/customers/` 페이지·목록·shell·api, `forms/`에 공통 폼·생성 폼·수정 폼). 서버 데이터는 oRPC + Query로 접근한다.
  - **등록**: 목록 위 "+ 고객 등록" → 우측 패널(좁은 화면은 위쪽). 중복 전화번호는 전화번호 입력에 오류로 표시하고 입력을 유지한다.
  - **수정**: 행의 "수정" 버튼 → 같은 패널이 수정 모드(기존 값 채움, 전화번호는 하이픈 표시)로 열린다. 저장 성공 시 목록의 같은 자리에서 값이 바뀌고, 중복(`CONFLICT`)은 전화번호 오류로, 이미 지워진 고객(`NOT_FOUND`)은 경고 알림 후 목록에서 내리고 패널을 닫는다. 닫으면 누른 행의 버튼으로 포커스가 돌아간다.
  - **삭제**: `deleteCustomer`와 테스트까지만 있고 화면 버튼은 없다(V1 스토리 밖).
  - **조회·갱신**: 저장 뒤 진행 중이던 이전 조회가 새 값을 덮지 못하게 취소한 뒤 캐시를 고치고 서버 순서로 다시 맞춘다.
- 확인한 것: client 전체 테스트 120개 통과(수정 시나리오 포함), 타입 검사 통과, 실서버에 같은 요청(`PUT /customers/{id}`, body는 name·phone)으로 수정 200·같은 번호 재저장 200·다른 고객 번호 409·잘못된 번호 400·없는 id 404 확인(테스트 고객은 삭제함).

### 공통 UI(`client/src/shared/ui/`)
`button`, `field`, `input`, `select`, `textarea`, `choice`(Checkbox·RadioGroup·Radio·Switch), `segmented-control`, `amount-field`(parseAmount/formatAmount), `table`, `badge`, `data-table`(상태 판정·다시 시도), `dialog`, `empty-state`, `skeleton`, `error-state`, `notice`(Notice·LiveNotice), `toast`(함수형, 루트 `<Toaster />`), `theme.stylex.ts`.
- `routes/`의 `-*-review.tsx`는 공통 UI 검토용 예시이며 업무 라우트가 아니다. `/`가 이를 조립한다.
- 기존 검증 한계: 실제 스크린리더·Safari/Firefox·실기기·OS reduced-motion은 미검증. Chrome DOM/AX와 에뮬레이션 결과만 있다. 이전 check의 포맷 실패·경고 기록이 있었으므로 현재 기준선은 새로 확인해야 한다.
